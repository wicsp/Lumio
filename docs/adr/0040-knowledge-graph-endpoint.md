# 0040 全库知识图谱：一次读出整个链接图

- 状态：Proposed
- 日期：2026-11-08
- 领域：数据 | Hub 与运行
- 影响：新增契约（向后兼容的新增，不改已有字段）：`KnowledgeGraphArgs`、`KnowledgeGraph`；新增只读路由 `GET /v2/knowledge/graph`。
  `docs/design/knowledge.md`、`web.md` 随实现同步修改。
- 实施说明：[K3-0](../tasks/K3-0-knowledge-graph.md)

## 背景

人类在 2026-11-08 要求做笔记的知识图谱。#115 已经用现有的单篇链接接口（`GET /v1/notes/<ref>/links`）实现了「以一篇笔记为中心」的关系图：
一层或两层，第二层最多展开 24 篇。这种做法画不了全库：全库图要对每篇笔记各发一次请求，几百篇笔记就是几百次往返，
而且每次都要重新解析。链接图本来就在 `index.sqlite` 里（ADR 0014、0018），Hub 一次查询就能给出。

## 决定

### 1. 接口

- `GET /v2/knowledge/graph`，只读，human 可用；参数 `KnowledgeGraphArgs`（查询串）：
  - `include_private`：缺省 false，规则与搜索、链接相同（私密笔记及指向它们的边默认不出现）；
  - `type`：可选，只要某一类笔记（如 `paper`）；
  - `include_legacy`：缺省 false，旧任务 / 项目 / 例行笔记不出现，与知识列表默认一致。
- 结果 `KnowledgeGraph`（严格对象）：
  - `nodes: NoteRef[]`：参与图的笔记，**包括没有任何链接的孤立笔记**（界面可以选择隐藏）；
  - `edges: { from: string; to: string; count: number }[]`：`from`、`to` 是笔记的**路径**（每篇都有，`NoteRef.id` 可能缺失）；
    同一对笔记的多条链接合并，`count` 为条数；自链接不出现；
  - `dangling: number`：悬空链接条数（只给数量，详情仍由 `lumio check` 列出）；
  - `generated_at`：索引的更新时间。
- 边的来源与链接图完全一致（ADR 0018、0022）：正文 `[[ ]]` 与 Markdown 链接，AI 区块内的链接、frontmatter `related`、代码块都不算。
  回收站（`.trash/`）中的笔记不出现。

### 2. 规模与边界

- 一次返回全量，不分页：个人 vault 在几千篇以内，结果是几百 KB 量级的 JSON；Hub 从索引直接读取，不重新解析文件。
- 不进入 agent 能力目录：agent 继续用 `knowledge.note.links` 按需走图。是否开放给 agent，等实际需要时另议。
- 布局完全在前端；Hub 不计算坐标、社区或排名。

### 3. Web

- 知识页增加「图谱」视图：力导向布局，节点按类型着色、按链接数定大小；可按类型筛选、隐藏孤立笔记；
  点节点打开笔记，悬停高亮邻居。超过 300 个节点时默认只显示链接数最多的 300 个，并提示可以按类型筛选。
- 单篇笔记的关系图（#115）保持不变，仍用单篇链接接口。

## 后果

- 好处：全库图一次请求；与「以一篇为中心」的关系图共用同一套链接规则，结果一致。
- 代价：新增一个只读接口与契约；前端的力导向布局在 300 个节点左右需要分批计算以免卡住界面。
- 否决的方案：
  - 前端逐篇调用链接接口拼出全图：请求数与笔记数成正比，慢且重复解析。
  - 在 Hub 里算好布局再下发：布局依赖屏幕尺寸与交互，放在 Hub 只会让契约变复杂。
  - 把图塞进现有的搜索结果：搜索有条数上限，也不是图的语义。
