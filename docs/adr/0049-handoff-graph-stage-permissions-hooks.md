# 0049 交接图、阶段权限与可选钩子；仓库规则与编排解耦

- 状态：Accepted（2026-11-10 人类在对话中批准方向；第 3 节各引擎的权限映射由实现者实测后记入修订记录）
- 日期：2026-11-10
- 领域：AI 协作与权限 | Hub 与运行 | 数据 | 流程
- 影响：修订 ADR 0032 第 5 节（交接计划从有序列表扩展为有向无环的交接图，增加阶段权限、钩子与自动完成）、
  ADR 0031 第 3 节；补充 ADR 0044（项目默认计划）。
  契约（均为向后兼容的新增，旧计划按线性计划读取）：`PlanAgentStage` 增加 `after`、`access`、`git`、`secrets`、`hooks`；
  `PlanCheckpoint` 增加 `after`；`HandoffPlan` 增加 `finish`；`PlanRun` 增加 `active` 与 `done`；`TurnHolder` 增加 `agents`，`Turn` 增加 `parallel`；
  `WorkProject` 增加 `default_plan`；`WorkTask` 增加 `grants`（无计划任务上已批准的权限）；新增提议种类「保存计划模板」；
  一轮结果增加权限申请（与提问同一路径）。
- 实施说明：[H1-0](../tasks/H1-0-handoff-graph.md)

## 背景

2026-11-10 两件事暴露了同一个问题：**编排写在了仓库规则里，而执行环境由 Lumio 决定，两边对不上。**

1. 作者在 Codex 里直接发布任务，Codex 按 AGENTS.md「交叉 review」与「分工」两节，自己在终端调用本机 Claude Code 复审并合并。
   Lumio 不知道这件事：本机没有 Claude、作者不想用 Claude 复审时都无从干预。
2. 作者把任务委派给 `codex@macsp`，Codex 按 AGENTS.md 第 9 条要先 `git fetch`，但 Lumio 以 `workspace-write` 启动 Codex，`.git` 受保护；
   Codex 转而请求 `lumio-runtime sudo`（root 级入口，本机未配置），以提问结束本轮。作者回复「好的」后续接同一会话、同一沙箱，得到同一个问题。

作者想要的开发方式：A 实现 → B 审核 → PR 的 CI 与本机试用同时进行 → 试用通过后，CI 通过即合并（未完成就等它完成后自动合并）→ 任务完成。

讨论中曾考虑由 Runtime 用固定脚本完成 Git、等 CI、部署与合并。作者否决：那是回到 n8n 式工作流。
agent 已经能做几乎所有事，Lumio 只需让人按自己的方式组织 agent 之间的交接；脚本可以有，但只是交接之间可选的钩子。

## 决定

### 1. 分层：Lumio 管谁、何时、权限；怎么做交给 agent 与仓库

| 层 | 负责 | 不负责 |
|---|---|---|
| 仓库（AGENTS.md、文档、脚本） | 工程事实：分支与工作区要求、检查命令、合入关卡（CI、安排了的 review）、本机部署方法 | 由谁做、何时做、交给谁 |
| Lumio 交接图 | 每一步交给谁、做什么、何时停下等人、每一步有什么权限、可选钩子 | 某个仓库怎么构建、部署 |
| Runtime | 本机有哪些 agent 及其隔离能力；按阶段权限启动 agent | 流程本身 |

- 必须保证「发生」或「不发生」的事，用**权限**保证，而不是用固定步骤：例如「检查点放行前不能合并」靠只有合并阶段拿到有合并权限的凭据，
  加上仓库的分支保护兜底；而不是由 Runtime 替 agent 合并。
- 仓库规则写成**调用方无关**的形式：要求只写结果与关卡，并要求 agent「只做被交代的这一步」；
  没有调用方安排下一步时（例如人直接在 Codex 里开工），做完交回人，不自行找别的 agent 审核或合并。
- 每一轮的固定说明（Hub 生成）补充：只完成本阶段；本阶段已有的权限；缺权限时**按第 3 节申请**，说明要什么、为什么，由人批准。
  鼓励按需申请，而不是绕过或放弃。

### 2. 交接图：有向无环，节点仍只有两种

- 节点仍是 **agent 阶段**与**检查点**（ADR 0032 第 5 节）。每个节点可写 `after: [阶段 ID]`；缺省为列表中的上一个节点，
  所以旧计划与只想要线性流程的人不用写 `after`。`after` 必须构成无环图，至少有一个 agent 阶段。
- **并行与汇合**：一个节点在它 `after` 的节点都交付后开始。没有后继的节点都完成时计划走完。
- **第一版并行限制**：同一时刻最多一个 `access` 为 `write` 或 `full` 的阶段在执行（同一工作区不能有两个写入者）；只读阶段可以任意并行。
  检查点不与其他节点并行：检查点开始前，它之前的并行分支都要结束。
- **打回**（`back_to`）不算图里的边，而是「重跑某个 agent 阶段」：目标阶段与它之后已完成的阶段都重新计为未完成。
  并行分支中有一个打回时，等同一批的其他分支结束，把各分支的汇报一起带入重跑的那一轮。轮数上限（缺省 8）计入所有并行轮次。
- **并行中的提问与失败**：某个分支提问或失败时，其他已在执行的分支继续到结束，然后轮到人（`answer` / `failed`，注明阶段）；
  人回答后只重跑那个分支（能续接会话时续接）。
- **轮到谁**：只有一个 agent 在执行时与现在相同；多个同时执行时 `holder` 为 `agents`、原因为 `working`，`parallel` 列出各分支的阶段、agent、Job 与轮次。

### 3. 阶段权限

agent 阶段可声明本阶段的权限，缺省值与现在的行为一致：

- `access`：`write`（缺省，可写工作目录）、`read`（只读）或 `full`（不受沙箱限制，以执行器账号运行；用于部署、重启本机服务这类工作区之外的操作）。
- `git`：缺省 `false`；`true` 表示允许写 Git 元数据（fetch、建分支、提交、推送）。
- `secrets`：本阶段注入的密钥名列表（如合并用的 GitHub 令牌），按 `${secret:…}` 规则只在执行节点解析，不进入提示与日志；其他阶段拿不到。

执行与如实声明：

- Runtime 按阶段权限启动 agent。`sandbox: os` 的引擎（Codex）由沙箱强制：`read` → 只读沙箱，`write` → `workspace-write`，`full` → 不使用沙箱，
  `git: true` 再放开工作区 Git 元数据的写入。**具体的 Codex 配置项由实现者在锁定版本上实测**，确认能放开 `.git`（含 worktree 指向的元数据目录）且不扩大到其他路径，结论写入修订记录。
- `sandbox: none` 的引擎（Claude Code、pi）无法强制只读或禁止 Git，权限只作为说明传给 agent。设置计划时界面与命令行要明确提示
  「该执行者无法强制此权限」；真正的约束依靠凭据隔离（`secrets`）与外部系统的保护（如 main 分支保护）。
- 阶段权限不能超出执行器登记的能力，也不绕过 ADR 0020：需要 root 的命令仍走高权限申请。

**按需申请权限**（人类 2026-11-10 补充：动态申请是好事，问题只在于申请没有走到能执行的地方）：

- agent 缺权限时可以随时申请，两条路按「需要什么身份」区分：
  - **需要 root 的系统命令**（装系统包、改系统配置）：沿用 ADR 0020 的 `lumio-runtime sudo`，一轮内申请、人批准后由 root 助手执行。
    前提是该执行器配置了 root 助手；没有配置时，Runtime 的拒绝信息要直接说明「此执行器未配置高权限助手」与配置方法，而不是只说不支持。
  - **普通账号能做、但本阶段没给的权限**（写 Git、`write` / `full`、某个密钥）：在汇报末尾单独一行写
    `<lumio-permission>git</lumio-permission>`（可写多项：`git`、`write`、`full`、`secret:<名称>`），并说明理由。
    Runtime 像提取提问一样提取它，这一轮以等人回应结束；人在卡片里「批准并继续」或「拒绝并说明」。
    批准时选择范围：只给接下来这一轮，或给这个任务的该阶段（没有计划的任务记在任务上）。批准后以新的权限续接同一会话继续。
- 两条路不混用：用 root 做普通账号就能做的事（例如以 root 运行 `git`）会在工作区留下 root 所有的文件，所以 Git 一类的需要走第二条。
  这是为了把申请送到能执行它的地方，不是限制 agent 申请。
- 2026-11-10 的情况按此规则是：Codex 以 `<lumio-permission>git</lumio-permission>` 结束本轮，你批准后它带着 Git 权限续接会话继续。

### 4. 可选钩子

- agent 阶段可声明 `hooks.before` / `hooks.after`，各为一条命令（argv 数组，不经过 shell；需要 shell 时显式写 `["bash", "-lc", "…"]`）。缺省没有钩子。
- 钩子由 Runtime 以执行器账号在任务工作目录运行，有超时（缺省 30 分钟，可写 `timeout`）；环境变量提供任务 ID、阶段 ID、轮次、工作目录，
  `after` 钩子另有本轮汇报文件的路径。钩子的输出记入这一轮的日志。
- `before` 失败：不启动 agent，轮到人（`failed`，注明钩子与输出末尾）。`after` 失败：这一轮按失败处理。
- 钩子会占用执行器的并发名额（例如等 CI），超时后按失败处理。
- 计划含钩子时，agent 提出的计划仍需人批准（ADR 0031 第 2 节），批准页面要完整显示每条钩子命令。

### 5. 计划走完自动完成

- `HandoffPlan.finish`：`review`（缺省，计划走完轮到人验收，与现在相同）或 `auto`（计划走完由 Hub 系统身份将任务标为完成）。
- `auto` 只允许用于**至少含一个检查点**的计划：人在检查点按「继续」就是验收，之后的阶段（如合并）成功即完成，失败轮到人。
  这样「完成只有人能决定」不变：人批准了含 `finish: auto` 的计划，并在检查点亲自放行。审计记录注明依据的计划批准与检查点操作。

作者的开发方式写成计划（修订后：合并后在 `main` 上验收，不在合并前试用）：

```text
implement   codex@macsp        write, git
merge       codex@macsp        write, git, secrets: github-merge
            hooks.before: gh pr checks <PR> --watch（等 CI；失败则轮到人）
deploy      codex@macsp        full                 说明：按 docs/local-deployment.md 从 main 部署 7420
finish: review                                      （计划走完轮到人，在日常实例上验收；不行就打回或 revert）
```

需要 review 时，在 implement 与 merge 之间加 `review  claude-code@macsp  read  back_to implement`。

### 6. 配置入口

优先级按人类 2026-11-10 的确认：

1. **一句话生成**：在 Assistant 里描述流程，AI 生成交接图并以「保存计划模板」提议给人，人在卡片里预览图形后保存。
   为此新增提议种类「保存计划模板」：agent 只能提议，模板仍只有人能保存（ADR 0031 第 2 节的边界不变）。
2. **项目默认计划**：`WorkProject.default_plan`（计划模板 ID，可清空）。人在 Today 点「委托」、任务还没有计划时，
   以人的身份套用项目默认计划并委派第一个阶段；没有默认计划时保持 ADR 0044 的单轮委托。agent 委派仍只能提议。
3. **列表编辑器**：从上到下的阶段卡片，「添加并行」把卡片放在同一行；不做节点连线画布。阶段可从内置角色（实现、审核、部署、合并）开始，
   角色只预填说明与权限，不是契约。保存时校验：执行者已登记、无环、`back_to` 指向 agent 阶段、并行写入限制、`finish: auto` 需要检查点、
   以及第 3 节「无法强制的权限」提示。
4. 任务套用模板后可单独修改（换执行者、删阶段），不影响模板。

派出前（每个 agent 阶段开始时）Hub 再检查一次执行者是否登记、引擎是否在线、所需权限能否满足；不满足时不派出，直接轮到人并写明缺什么，避免开一轮只得到同一个问题。

### 7. 不在本 ADR

- 并行写入（每个写入分支各自的 worktree）、条件分支、跨任务的部署排队：等用上第一版之后再定。
- 按对话语义授权（ADR 0031 第 5 节）；自研 agent 框架的按步骤动态授权会以「阶段权限」为起点，另写 ADR。

## 后果

- 好处：谁来审核、要不要审核、用哪台机器的哪个 agent 都在 Lumio 里可见、可改、可校验；仓库规则在 Lumio 内外都适用。
  「放行前不合并」由凭据隔离保证，不靠 agent 自觉。交接图仍只有两种节点，不写 `after` 时与现在完全一样。
- 代价：并行带来汇合、打回与提问的组合规则。`PlanRun` 保留 `stage`，只新增可选的 `active` / `done`，旧数据不迁移（见修订记录）。
  `sandbox: none` 的引擎无法强制权限，只能如实提示。
- 风险：钩子是任意命令，含钩子的计划必须经人批准并完整展示；长时间等待的钩子占用执行器并发名额。

## 修订记录
- 2026-11-10（H1-2 契约起草，随 PR 待人类批准）：契约落地方式细化——`PlanRun` 保留 `stage`（并行时为第一个执行中的阶段），新增可选 `active`（≥2）与 `done`，缺失按线性前缀理解，不迁移旧数据；
  权限批准为新命令 `work.task.grant`（范围 `next_round` / `task`，缺省批准后续接）；`AgentRun` 增加 `permissions` / `hooks`，`JobResult` 增加 `permission`；
  `RuntimeRegistration` 增加可选 `features`（`stage_permissions`、`hooks`、`permission_request`），Hub 只把新字段发给声明了对应能力的执行器，旧执行器不受影响。
- 2026-11-10（H1-4 执行器实测）：macOS 上 Codex 0.166.0 的命名权限配置可沿用 `:workspace`，仅覆盖 Git 元数据。普通仓库授权其 `.git`；linked worktree 须同时明确授权共有 Git 目录和当前 worktree 的元数据目录，仅授权共有目录时 `FETCH_HEAD` 仍不可写。通过临时仓库及回环 Git 服务验证 fetch、commit、push，`.codex` 和工作区外的测试目录仍拒绝写入。执行器从实际 checkout 解析路径，版本或目录不符合时拒绝该轮。
- 2026-11-10（人类批准）：`RUNTIME_FEATURES` 增加 `privileged_helper`，`JobResult` 增加 `privileged_unavailable`（只含程序路径），让人在设置页和任务卡片上知道哪台执行器还没装高权限助手、怎么装。
- 2026-11-10（人类批准）：否决「合并前试用、试用通过再合并」。合入 `main` 的关卡改为 CI 通过与安排了的 review，人类在合并后的 `main` 上验收（#156）。第 1 节表格与示例、第 5 节作者的计划示例、第 7 节与后果中的相应措辞随之修改；背景中作者原先想要的方式保留为历史。
