# 0069 Job 实时进度与同轮人工介入

- 状态：Implemented（2026-11-17 人类批准，PR #235）
- 日期：2026-11-17
- 领域：契约、执行协议、存储格式、权限与安全、发布与升级兼容
- 关联：ADR 0019、0020、0025、0032、0042、0049、0063、0068
- 任务：[Job 实时进度与同轮人工介入](../tasks/job-live-progress-and-control.md)

## 背景

Codex Job 已经输出 JSONL，但 Runtime 在进程退出后才解析报告。Claude Code Job 只请求最终 JSON。
Hub 用心跳标记 Job 正在运行，Web 在运行时拿不到工具与步骤，报告和日志归档又要等 Job 结束。
Troupe 的阶段总览、最近活动和置顶「等你处理」能解释这种等待。Lumio 的原生 Codex Assistant 已验证带序号的事件补读和与进程实例绑定的审批，
但它的连接、沙箱、工作目录和会话归属于 Assistant，与可以在任意获准项目目录中运行的 Job 有不同边界。

## 决定

### 1. 运行状态、活动和任务交接各有来源

- Job 的记录和最终结果仍由 Execution 管。Work 的任务结局、当前交接和检查点仍由现有业务流程推进。一次派出对应一个 Job。
  同轮等待是 Job 的实时视图，只有已确认的 Job 结果才能触发 Work 的轮末交接。并行阶段有独立的 Job 视图。
- 新的 `JobLiveView` 关联 Job ID，包含已知的派出、启动和最后心跳时间，最近已观察活动的时间，执行器的连通状态，
  当前观察阶段（准备、引擎运行、有活跃工具、等待人工、收尾）、最后已提交的事件序号及有界的活动摘要。
  一个 Job 可以同时有多个工具在运行，阶段和活跃工具按同一事件前缀生成。
  快照可表达实时能力不可用、当前没有新事件、历史前缀已过期、执行器失联、已请求停止但仍待确认。
  心跳、新活动和终态是不同的信号。引擎时间用于展示，Hub 的接收时间用于连接新鲜度判断。
- 新的 `JobActivityEvent` 由 Schema 定义为严格的可辨识联合。事件包括启动、前后钩子阶段、
  确认观察到的工具开始或结束、引擎活动摘要、已知错误和省略提示、人工请求打开及关闭。工具事件带轮内稳定的工具 ID、
  种类及允许展示的标签，结束带已知结果。引擎能力有差异时，只展示它实际提供的信号。
  原始消息、工具输入输出、内部推理和任意供应商事件留在各自的既有处理边界。
- Job 活动正文仅对 human 开放。CLI 和 Web 共用
  `GET /v2/execution/jobs/:id/live` 和 `GET /v2/execution/jobs/:id/events?after=<sequence>&limit=<limit>`。
  活动页携带 `first_available`、`next_after`、`has_more` 与事件，按序号升序，缺省 `after=0`、
  单页不超过 200 条。Hub 告知缺失前缀，客户端用快照恢复并显示缺口。原始运行归档继续沿用独立的文件接口。

### 2. 通过现有 Job 2 协议协商及交付

- Runtime 在现有登记请求的 `X-Lumio-Features` 头声明 `job-activity`，Hub 用响应头确认。登记请求体沿用 Job 2，旧 Hub 可忽略头。
  确认后 Runtime 在活动端点按引擎、平台和已验证版本登记进度、审批、提问及纠偏能力。Hub 据此决定能否派出交互 Job，
  启动时 Runtime 再验证一次。旧 Runtime 可继续收发原 Job，旧 Hub 无扩展确认时 Runtime 继续用原协议。
  缺少活动的历史 Job 视图明确标记无实时数据。
- Runtime 主动调用专用的 `POST /v1/runtime/job-activity/sync`，独立于结果、队列和文件同步。
  请求带 Job ID、lease、最多 64 条事件和动作回执，响应带已确认的连续序号及待交付的动作。Schema 限制各字段长度和每批条数，HTTP 请求体上限 256 KiB。
  Runtime 给已筛选的事件分配单调序号，在本地持久化后发送。Hub 以被指派的 Runtime、Job、lease 和序号验证归属与去重，
  先保存后确认。重复批确认同一前缀，冲突内容和跳号拒绝并返回当前确认位置。短时断线补发活动，查询者重连从游标补读。
- 活动按有界批写入，通常合并在 1 秒内上报。每轮最多保留 2,048 条普通活动，优先合并高频消息，额度耗尽时记录省略。
  开始、收尾、人工请求与决定回执使用独立受限容量。达到人工请求容量时拒绝新的同轮请求并显示理由，轮末仍可交接给人。
  活动数据丢失或 Hub 暂不可达不阻塞非交互 Job 交付最终结果。
- Hub 用新的可选表保存实时视图、近期活动、动作与回执。现有 Job、任务和日志记录无需重写或回填。
  Job 结束后普通活动保留 30 天，审批另留原有审计范围以内的操作事实。旧程序可忽略新增表。
  只接受原 lease 正常结束后 24 小时内的迟到观察事件用于补齐历史，终态和已关闭的人工请求保持封存。
  运行期间连接中断时，Hub 显示最后确认时间。执行进程状态成为 unknown 时，禁止自动重放输入、工具或 Job。活动读取游标与 Runtime 上报确认分别推进，历史清理不改变已确认序号。

### 3. 引擎适配与同轮人工介入

- 非交互执行从 Codex `exec --json` 和 Claude Code `-p --output-format stream-json --verbose` 增量解析。
  等待模型或子进程长时间无输出时，用已知心跳和最近活动描述现状。解析在 Runtime 内按行和字节边界处理，
  丢弃未知事件类型或超限行，优先保存当前会话 ID 和最后一条有效的最终结果。Codex 保留最后回复文件语义。
  pi、命令及较旧引擎可只有执行器阶段和心跳。
- Work 的手动委派、计划中 Agent 阶段及独立 Agent Job 可以显式选择交互模式。缺省沿用非交互执行，定时无人值守运行沿用现有模式。
  计划预览与委派表单显示交互能力及实际隔离级别。若明确要求交互但执行器不支持，派出前给出理由；此前已领取而能力发生变化时，
  在启动进程前失败并交回。避免在人以为能审批的情况下启动无人值守引擎。
- Codex 交互适配器使用项目目录中的 App Server，通过私有 stdio 接收工具、提问、审批事件，
  将纠偏输入和中断绑定到准确的活动 turn。复用现有 JSON-RPC 与事件处理机制，继续按 Job 的阶段权限创建沙箱。
  对引擎提出的沙箱外执行，只有独立的 OS 隔离能证明仍在批准范围内才允许交给人决定。Claude Code 用官方 Agent SDK 的 `canUseTool` 和 `AskUserQuestion` 接入工具审批和提问，
  通过受控的流式输入和取消处理轮次。Claude 对额外用户输入的实际消费时机必须按引擎回执展示。
  交互适配器使用相应 Runtime 的明确授权连接，按已验证版本和认证、隔离能力登记。Claude 交互模式禁用 `bypassPermissions`，
  Shell、Git 写入和扩展能力依 Job 策略限制，不能假定每次工具执行都会走 `canUseTool`。严格权限由运行时沙箱强制，
  严于设备能力的阶段拒绝启动。
  计划阶段权限、Git、工作目录、凭据注入、钩子和高权限助手校验都必须经现有执行边界。
- 同轮请求可为工具授权或问题。请求带 Job、进程实例、会话与轮次标识、唯一的请求 ID、过期时间、
  类型化请求内容和允许的动作，默认 5 分钟过期后拒绝执行。授权只适用于这一项已核对的请求；
  Web 展示可复核的命令或文件范围、工作目录、引擎、理由和隔离级别。无法安全展示完整授权对象时只允许拒绝。
  既有阶段增权和 root 助手仍由各自审批决定。同轮批准不增加阶段允许的路径、Git 权限、网络或密钥。
- `POST /v2/execution/jobs/:id/actions` 仅 human 可用。动作含 `request_id`、目标进程实例及 turn，
  审批或答复还必须带当前提示 ID；区分答复、同意一次、拒绝和纠偏输入。停止由现有取消入口登记，
  交互引擎收到中断后由 Runtime 回报结果，进程无法确认时交给现有 unknown 流程。
  Hub 校验 Job 活跃、现有权限、请求状态与参数后持久登记；重复提交同一动作返回同一回执，更换参数或提交旧请求冲突。
  Runtime 再检查 lease、实例、轮次、请求和过期时间，串行处理，并持久登记已尝试交付的动作以防重放。成功或拒绝由引擎回执确认。
  等待送达、已送达、已应用、过期、结果未知必须可区分。收到 Job 取消请求时不再签收新的同轮决定，
  Runtime 观察到取消后清掉待处理请求。若进程失联后动作效果无法确认，回执标记 unknown，等待核查。

### 4. 展示、通知与敏感信息

- Today、任务详情和执行详情各使用同一 Job 实时摘要。卡片展示引擎、耗时、最近可证实活动、
  以及最后心跳或更新时间。详情提供阶段、工具和改动时间线，并保留可点击的历史归档。旧页重开时恢复当前请求与游标。
  新的同轮请求进入「需要你处理」，按请求 ID 去重并深链接到 Job，无需改 Work 的 turn。
  主动推送限明确等人且仍有效的请求，沿用既有通知偏好。CLI 可观察同轮状态，需介入时输出 Job 链接，用户在 Web 处理。
- Runtime 在写活动或发送工具细节前复用已注入凭据的脱敏，按字段白名单与长度限制输出。
  路径用安全的项目相对名，命令标签用裁剪后的安全预览。输入答复及完整审批预览只在权限校验后的必要范围内传递，
  不进入原始活动简报、推送和审计正文。审计记录授权人、Job、轮次、请求类型和动作结果。
  浏览器以普通文本渲染引擎文字，对人工请求只渲染符合 Schema 的选项。

## 取舍

- tmux 画面识别与尾读供应商私有会话文件适合观察外部启动的终端，本文范围是 Lumio 自己派出的 Job。
  直接消费官方事件可区分工具、审批和轮次标识，并降低终端布局或语言变化造成的误判。
- 直接导出原始日志会把引擎私有格式、任意 stdout 和大量输出带进面向人的接口。单独有界事件流可在保留现有归档的同时提供可恢复的进度。
- 首版沿用现有客户端的游标轮询。状态和增量语义与传输解耦，后续可根据频率与延迟测量决定是否推送。
- Assistant 原生会话与 Job 共用低层机制，仍各自管理授权、模型上下文和结果。这样项目阶段权限与工作流不会依赖 Assistant 对话。
