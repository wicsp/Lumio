# 0014 Hub 与 AI 访问：提议边界、CLI + skill、令牌、链接、搜索、写入路径

- 状态：Accepted（P1 实现）
- 日期：2026-10-25
- 领域：Hub 与运行、AI 协作与权限、安全
- 合并自：ADR 0006、0010、0011（三者均未实现，已删除原文件，内容全部并入本 ADR）

## 背景
P1 要实现 Hub：文件监听与自动补全、索引、搜索、提议队列，以及供 AI 使用的查询命令。
这些设计原先分散在三条 ADR 里：0006（AI 只能提议）、0010（AI 通过 CLI + skill 访问）、0011（Hub 的具体设计），
彼此引用、多次互相修订。三者都没有实现，按 ADR 0013 合并为一条。

几个背景事实：
- vault 里的知识价值主要来自"哪些想法、论文、实验之间有关系"。如果 AI 可以随意建立链接，链接图会很快被
  大量看似合理、实则未经思考的关系淹没，人也会失去对知识结构的掌控。
- 接入的 AI 主要是 Claude Code、Codex、pi，都运行在有 shell 的环境里（Mac 或服务器）。
- 2026 年 MCP 的主要问题是成本：工具定义常驻上下文，单个服务器几十个工具就可能占用数万 token。
  skill 平时只常驻一行简介，CLI 在被调用前不占上下文。pi 于 2026-10 的 1.0 版本以 Codemode 方式加入 MCP，
  MCP 从"所有数据都经过模型的通道"退为"工具目录"。通行的划分是：有 shell 的本地 agent 用 CLI + skill，
  没有 shell 的客户端、托管服务、需要 OAuth 的场景用 MCP。
- 实测：SQLite FTS5 的 trigram 分词器对两个汉字的查询（如"来源"）返回空结果。

## 决定

### 1. 人与 AI 的边界：AI 提议，链接由人建立
- AI 可以：查询；新建想法和论文笔记；**提议**链接；重写明确标为 AI 产出的内容，即正文中的
  `<!-- lumio:ai … -->` 区块（格式见 ADR 0012 第 3 节）。
- AI 不可以：直接写入人拥有的链接（正文里的 `[[...]]`、frontmatter 的 `related`），也不可以修改人写的正文。
- AI 的提议存放在 Hub 的提议队列中，由人接受或拒绝后，才由 Hub 写入 vault。
  **这条规则由 Hub 在写入时强制执行，不靠事后 review。**
  具体机制见 ADR 0016：提议是"需要批准"的操作，由 Hub 的统一授权入口产生。
- 接受一个提议后，这条链接就属于人；之后 AI 不得自行删除或改写。

### 2. AI 的入口：CLI + skill；MCP 推迟
- **能力只实现一次，入口只是外壳。** 查询逻辑在 `packages/core`，Hub 与本地 CLI 共用；
  需要强制执行的规则（提议、私密访问）由 Hub 执行。CLI、以后的 MCP 适配器都不重写业务逻辑。
- P1 中 AI 通过 `lumio` 的查询与提议命令（`search`、`show`、`links`、`propose`，全部支持 `--json`）
  和 `skills/lumio/SKILL.md` 使用 Lumio。Claude Code、Codex、pi 共用这一份 skill。
- MCP 只在出现**没有 shell 的客户端**需求时（例如在手机 Claude App 里查询笔记）才实现：一个把 MCP 工具
  映射到 Hub API 的薄适配器，走 ADR 0007 的 HTTPS + 令牌，不含业务逻辑。

### 3. Hub 的运行状态与 vault 分开存放
- **vault**：知识的唯一事实来源，只放 Markdown（ADR 0007）。
- **Hub 状态目录**：默认 `~/.local/share/lumio/`，可配置，不在 iCloud 中。包含：
  - `index.sqlite`：**派生**索引（实体、链接、全文），可随时删除重建。
  - `hub.sqlite`：**运行状态**（令牌、提议队列，P2 起还有 job），不是知识，无法从 vault 重建。
- 理由：提议、令牌、job 是 Hub 的工作数据，不该出现在 Obsidian 里，也不该跟着 iCloud 同步到手机。
- `hub.sqlite` 需要单独备份，P1 中提供 `lumio hub backup`。

### 4. 什么算"链接"
- 两种来源都计入链接图：frontmatter 的 `related`（列出 ID），以及正文中的 `[[名称]]`
  （按文件名解析；可带 `|别名`、`#标题`，解析时去掉）。两者都属于人。
- **接受 AI 的链接提议时，Hub 只写 frontmatter 的 `related`，永远不修改正文。**
- 无法解析的 `[[名称]]` 记为"悬空链接"，在结果中标出，不报错。
- AI 区块中的 `[[ ]]` 不计入人拥有的链接图。

### 5. 搜索
- SQLite FTS5，`trigram` 分词器，覆盖中文和英文的子串搜索。
- **查询少于 3 个字符时退回 `LIKE` 子串匹配**。
- 搜索范围：标题、正文、作者、citekey、tags。

### 6. 令牌与私密实体
- 令牌分两种角色：
  - `human`：所有操作，包括接受、拒绝提议。
  - `agent`：查询与提交提议，**不能接受或拒绝提议**。
- **私密实体**（ADR 0012，`life/` 下）默认不出现在任何查询结果中：
  - `agent` 令牌在任何情况下都查不到；
  - `human` 令牌须显式传入 `--include-private`（API 参数 `include_private=true`）。
  - 本地模式（不经过 Hub）无法分辨调用者，只能做到默认排除。直接读文件的 agent 需要在沙箱配置中排除 `life/`。
- 令牌只在创建时显示一次，Hub 只保存 SHA-256 哈希；可以单独吊销。
- 角色属于**身份**，令牌属于身份；记录"谁"时用身份 ID，不用令牌名称（ADR 0016 第 1 节）。

### 7. 写入路径
- **修改已有内容的程序写入必须经过 Hub**：接受提议（P1）、程序字段的更新（ADR 0009）。没有 Hub 时无法使用。
- **新建笔记和元数据补全**（`lumio new …`、`lumio sync`）可以本地执行：它们只新建文件或补全缺失的元数据，
  不改动已有内容，性质等同于人在 Obsidian 中新建文件；Hub 的文件监听会照常处理这些文件。
- **查询**两种模式都支持：设置了 `LUMIO_HUB_URL` 时走 Hub，否则直接读本地 vault。

### 8. 自动提交
- Hub 在 vault 无变化达到一段时间后（默认 5 分钟，可配置）自动提交一次，提交信息形如
  `lumio: auto-save 3 files`。vault 没有 git 仓库时跳过，不报错。
- Hub 启动时先完整执行一次补全与索引，覆盖 Hub 未运行期间（Mac 休眠、iPad 编辑）的改动。
- **提交前检查疑似卡号**（ADR 0012）：含疑似卡号的文件不提交、不进入全文索引，在状态中提醒人删除；
  提醒中只给出文件路径，不回显数字。其余文件照常提交。

## 后果
- 好处：链接图始终反映人的判断；AI 权限在接口层强制；知识与运行状态分离；中文短词也能搜到；
  不需要 Hub 也能用全部查询功能；上下文成本低，三家 agent 共用一份 skill；协议换代时只需替换最外层。
- 代价：每条链接都需要人点一次"接受"；多了一份需要备份的 `hub.sqlite`；仍有两条写入路径（Hub 与本地）；
  没有 shell 的客户端在 MCP 适配器完成前无法访问 Lumio；CLI 的 `--json` 输出成为事实上的接口，需要保持稳定。
