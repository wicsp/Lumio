# 0016 操作、身份与授权：为以后的 AI 权限系统预留接口

- 状态：Accepted（P1 实现）
- 日期：2026-10-25
- 领域：AI 协作与权限、Hub 与运行、安全
- 影响：ADR 0014 第 1、6 节，`packages/schema`（actor、operation、proposal、api）

## 背景
以后要做一套完整的 AI 权限管理，以及 Agent 的身份与生命周期管理：AI 不直接改文件，只能请求执行某个操作；
程序校验这个操作是否合法、这个 AI 有没有权限；没有权限时生成审批请求，带着判断所需的信息交给人，
人可以在和 AI 的对话里直接批准。

这套系统现在不做。但 ADR 0014 原来的 P1 设计里有两处，现在不改以后会很贵：
1. **"谁在操作"就是令牌名称。** 提议的 `author`、`decided_by` 存的是 `claude-code@mac` 这样的令牌名。
   令牌是凭证，不是身份：会被吊销、重发，一个 agent 也可能有多把。身份与生命周期必须挂在一个稳定的 ID 上。
2. **提议只能表示"加一条链接"**（`kind: "link"` + `from` + `to`）。以后要审批别的操作就得重写提议表和所有相关代码。

P1 还没有开始实现，现在改几乎没有成本。

## 决定

### 1. 身份与令牌分开
- 新增**身份**（Actor，ID 前缀 `act`）：人和每个 AI agent 各是一个身份。P1 中身份只有名称和角色（`human` | `agent`）。
- **令牌属于身份**：一个身份可以有多个令牌，每个令牌可以单独吊销。令牌本身不是身份。
- 提议、审计记录、日志里记录的都是**身份 ID**（日志可以同时记令牌标签，便于排查），不再用令牌名称表示"谁"。

### 2. 每次修改都是一个有名字的操作，只有一个入口
- 程序对 vault 的修改统一表示为**操作**（`Operation`）：`{ op: "<名称>", args: { … } }`。P1 只有 `link.add`。
- Hub 只有一个写入入口：先 `authorize(身份, 操作)`，再执行。查询请求同样先经过授权（P1 中只是检查角色与私密访问）。
- 以后换成完整的权限系统时，只替换 `authorize`，不改调用方。

### 3. 授权结果有三种：允许、拒绝、需要批准
- **允许**：立即执行。
- **拒绝**：返回 403，不执行。
- **需要批准**：不执行，生成一条**提议**，提议里原样存放这个操作；人接受后，Hub 执行这个操作。
- P1 的规则表：`human` 角色一切允许；`agent` 角色查询允许（私密实体除外），`link.add` 需要批准，
  决定提议、访问私密实体一律拒绝。
- "AI 提议链接"因此不再是一种特殊接口，而只是"agent 请求了一个需要批准的操作"。

### 4. 拒绝和需要批准时，返回机器能读的信息
- 错误响应统一为 `ApiError`：错误代码、给人看的说明，以及被拒绝的操作、拒绝原因、相关提议 ID。
- AI 拿到这些信息，就能在对话里告诉人"我想做什么、为什么需要你批准、提议 ID 是多少"。

### 5. 每次程序写入都留下审计记录
- Hub 在 `hub.sqlite` 里记录每次授权与执行：时间、身份 ID、令牌标签、操作、授权结果、提议 ID、执行结果。
- Hub 执行操作后**立即单独提交**，提交信息末尾带
  `Lumio-Actor: act_…`（执行者）、`Lumio-Proposal: prop_…` 与 `Lumio-Approved-By: act_…`（经提议执行时）。
  目标文件若有尚未提交的修改，先把这些修改作为一次普通的自动保存提交，再执行操作，保证归属清楚。
- 自动保存的提交（人在 Obsidian 里的修改、补全器的补全）不带 `Lumio-Actor`，因为无法确定是谁改的。
- 这些记录必须从第一天开始写：历史无法事后补。

### 现在明确不做
权限规则语言、身份的创建/暂停/过期等生命周期、按字段细分的权限、权限委托、审批界面。
它们以后都接在第 2–4 节留好的位置上。

## 后果
- 好处：以后的权限系统只替换 `authorize`；新增可审批的操作只需在契约里加一种操作；身份与凭证可以独立管理；
  AI 能拿到足够的信息向人解释；从第一天起就有完整的审计记录。
- 代价：P1 多一张身份表、一张审计表和一组身份管理命令；提议的契约稍微抽象一点；
  Hub 的程序写入不再合并进自动保存，git 历史里会多一些小提交。
