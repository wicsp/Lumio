# 0025 四个业务模块与混合存储：知识、工作、执行、助手

- 状态：Accepted（2026-10-31 人类批准，实施中）
- 日期：2026-10-31
- 领域：工程基础 | 数据 | Hub 与运行 | AI 协作与权限 | 安全
- 影响：模块依赖、Task/Project/Routine 的事实来源、程序写入与派活、查询与迁移契约、内置 AI 助手。
- 审批范围：第 1–9 节的目标与约束，以及范围内必要的契约细化与代码重构；具体 Zod 契约由 Claude 起草并交叉复核。
- 实施说明：[R0-0](../tasks/R0-0-four-module-refactor.md)。不迁移真实数据，不修改实际安装的服务。

## 背景

当前知识笔记、项目和任务共用 Markdown 实体与链接索引。Hub 的任务模块同时负责文件触发、
派活、会话输入、SQL、结果展示和写回；例行任务还从普通任务模块引用共用规则。
这使工作管理依赖知识目录和笔记格式，执行状态又同时分布在文件和数据库中。

目标需要独立支持知识管理、项目任务管理、设备执行和内置 AI 助手，并允许使用数据库、Markdown、JSONL
等不同数据格式。业务模块应按职责划分，存储格式不应决定模块边界。
正文需要支持外部编辑器，结构化状态通过 Lumio 修改。

## 决定

### 1. 四个业务模块与独立的 Runtime

| 模块 | 拥有的数据和规则 | 不拥有 |
|---|---|---|
| Knowledge | 论文、来源、想法、知识文档、引用和知识链接；知识读写与检索 | 任务进度、执行状态、助手对话 |
| Work | Project、Task、子任务、依赖、负责人、描述、讨论和进展 | agent 进程、知识笔记正文、引擎会话 |
| Execution | Job、Routine、设备能力、引擎会话信息、执行结果和产物关联 | 整个 Task/Project 的完成决定 |
| Assistant | 对话、消息、助手轮次、上下文、记忆与偏好、Agent 循环 | 其他模块的数据存储与授权决定 |

- 四个模块先部署在同一 Hub 进程中；每台执行设备保留独立 Runtime，通过 HTTP + job 协议主动连接 Hub。
- Knowledge 不依赖 Work；Work 在没有知识目录时也能使用。Execution 接受独立执行请求，不要求存在 Task。
- 人工任务无需 Job；一次 Task 可以经历多次 Job。Job 成功不自动把 Task 标成 done。
- Assistant 对话与 Work 讨论分别归所属模块；普通助手回复不要求创建 Job。
- Routine 归 Execution，表示计划与执行模板；定时创建任务等跨模块行为通过协调流程完成。
- 内置助手的 Agent 循环与模型适配器分离；Runtime 管设备、进程、队列和结果交回。
  首个助手切片用注入的模型与工具接口验证，不顺带建设模型路由或完整的自动多 agent 协作。
- 现有 Experiment 的工作规划、执行产物、研究结论分别由 Work、Execution、Knowledge 表达，保留来源关联。
  Post/Asset 暂保留原格式兼容，不在本次加入内容发布或资产管理业务。

### 2. 分层与代码依赖

每个模块包含业务规则、应用用例和能力接口；SQL、文件、网络和进程操作由具体适配器实现。
业务规则不做 I/O，应用用例只通过窄接口使用外部能力。

| 位置 | 职责与依赖 |
|---|---|
| `packages/schema` | 按领域组织公开契约与格式版本，仍只依赖 zod |
| `packages/knowledge`、`packages/work`、`packages/execution`、`packages/assistant` | 各自的规则、用例、能力接口；依赖 schema，不导入其他业务包的实现 |
| `packages/storage` | 按模块组织 SQLite、Markdown、JSONL、文件与索引适配器；实现业务包公开的存储接口 |
| `packages/api-client` | Hub 客户端，依赖 schema |
| `apps/hub` | HTTP、身份接入、模块组装、后台处理与跨模块协调；注入具体实现 |
| `apps/runtime` | 设备执行服务、可靠队列、进程和引擎适配；与 Hub 只通过协议通信 |
| 各客户端 | 接收输入、展示结果，通过 API 使用同一组用例 |

- 跨模块能力由调用方声明窄接口，由 Hub 组装，不形成业务包之间的循环依赖。
- Storage 不决定 Task 的状态变化等业务规则；业务包不反向依赖 Storage。
- 文件监听只把文件变化转为 Knowledge 的更新请求，不拥有全局写入队列。
- 公共基础设施涵盖身份/审批/审计、事务、交付、文件、搜索和可观测性；有状态能力有明确表归属和接口。
  下载、升级、诊断等已有重复实现按实际共用范围提取，不全部塞进新的通用工具箱。
- `core` 按迁移顺序拆解；旧入口可作临时转发，不在其中新增四套业务实现。
- 依赖检查需要验证业务包之间的隔离、业务包不依赖具体适配器、原有 packages/apps 边界和无循环。
- 不预先新增第三方依赖。实现确需依赖时，按 AGENTS.md 说明理由与替代方案。

### 3. 权威来源与存储

| 数据 | 权威来源 | 其他副本 |
|---|---|---|
| 知识正文、随知识文件维护的元数据 | Markdown + frontmatter | 数据库为索引与派生副本 |
| Project/Task、关系、状态、负责人、期限 | SQLite 业务表 | Markdown 展示和导出为派生物 |
| Work 描述、讨论 | 数据库，正文可用 Markdown 语法 | 外部编辑副本和导出不独立决定状态 |
| Assistant 对话、消息、上下文记录、记忆 | 数据库 | JSONL 可作追踪或导出 |
| Job/Routine、执行配置、最终结果和恢复状态 | 数据库 | 过程日志不反向决定业务状态 |
| 工具细节、流式输出、运行过程 | JSONL 或原始日志文件 | 数据库登记所属运行和归档状态 |
| 附件、数据集、实验原始产物等 | 文件存储 | 数据库登记文件 ID、校验和业务关联 |
| 全文、向量、汇总视图 | 派生存储 | 可从权威来源重建 |

- 单 Hub 使用一份本机业务数据库；Runtime 各自保留本地队列库。所有客户端通过 Hub 修改结构化状态。
  活跃数据库不放在知识同步目录中，不通过文件同步工具合并。
- 不因重构先改数据库文件名；从现有 `hub.sqlite` 增量迁移，保留身份、令牌、审计和历史 Job。
- 模块拥有自己的表与迁移；内部可使用外键，跨模块不直接读写或 JOIN 对方内部表，不做隐式级联删除。
  共用数据库不等于共用业务所有权。
- 常用筛选字段、关系和约束用明确的列与关系表；多变配置可使用经 schema 校验、有版本的 JSON。
- ID 保持稳定，路径只是文件定位信息。执行时保存输入快照、正文版本与来源，不依赖后来可变的文件。

### 4. 正文、编辑与派活

- Knowledge 的 Markdown 文件可以直接用外部编辑器修改；现有知识补全、引用与隐私规则继续适用。
- Task/Project 的描述属于 Work，不因使用 Markdown 语法而成为知识笔记。
  外部编辑采用“读取正文与版本 → 打开编辑副本 → 校验版本并提交”的流程；冲突时保留编辑结果并明确报错。
  只修改正文，不把状态、负责人等结构化字段放进编辑副本。
- 结构化状态经 Work 用例修改。保存正文和修改负责人不隐式派活；派出/继续是明确操作。
- 任务生命周期、负责人、当前执行情况分别表达。新模型中 Job 结束不强制改负责人，除非人明确要求交接。
- 保留同一任务默认同时只有一轮执行的约束；paused/done/cancelled 不派出，暂停或取消可以要求取消当前 Job。
  取消请求与设备已停止分开记录，不能把请求成功当作进程已经停止。
- 续接同一 agent/设备时可使用引擎会话，否则发送固定的任务输入和必要历史。
  人的新意见用明确消息或版本差异表达；不把整篇笔记里所有新增文字都当成新的指令。
- 迁移后的控制路径不再监听旧 frontmatter 派活；旧文件编辑不能触发执行或覆盖数据库。

### 5. 跨模块流程、事务与可靠交付

- “从笔记创建任务”“给任务派出 Job”“把执行结果保存成知识”由 Hub 的协调流程调用模块公开用例。
  协调层不自己实现领域规则或修改内部表。
- Work 保存资料引用，展示时经 Knowledge 的接口读取可见信息。引用、输入快照、保存新知识是不同操作。
  来源不存在或不可见时允许保留引用，不返回来源内容；删除知识不删除任务或历史结果。
- 共享数据库内确需一起生效的变更由显式事务范围协调，各模块的存储接口参加同一事务。
  事务内不等待模型、网络、进程、文件归档；不向业务用例泄露原始数据库连接。
- 派活事务内保存 Work 执行关联、Execution Job、审计和待交付记录；提交后才向 Runtime 交付。
- 结果先由 Execution 持久化，再通过可靠记录更新 Work；通知和生成知识失败可以单独补做。
- 请求与结果有去重标识；重放交付不等于重新执行。实际执行是否发生不明时进入可核查状态，不自动重跑。
  保留已有 lease/所有权校验、本地先存后确认、结果先存后交回以及当前协议兼容性。
- 文件先准备并校验，再登记可用状态；中断后可重试登记或清理孤立暂存文件。
  日志归档状态与 Job 完成状态分别表示。
- 跨模块查询由组合接口完成；确需汇总索引时使用可重建、标明延迟的派生视图，并执行源模块权限规则。

### 6. JSONL、文件和备份

- 自有 JSONL 记录包含格式版本、运行 ID、事件 ID、运行内顺序、带时区时间、事件类型及经校验的负载。
  具体字段、ID 前缀和格式版本待 schema 提案批准；原始 agent 输出另行保留，不伪装成统一格式。
- 每个日志流单写入者，使用分段归档。读取时区分活跃流的不完整末行、归档截断与中间损坏，不能一律忽略解析错误。
- 执行状态、最终结果、用户消息和审批决定以数据库为准，不能只靠工具追踪 JSONL 恢复控制状态。
- Runtime 在 Hub 确认结果或文件归档前保留对应待交付数据；登记校验值与归档位置，重复交回可识别。
- 知识目录保存知识文档和适合随文档保存的附件；Hub 数据目录保存业务库、托管产物和索引；Runtime 保存队列和执行日志。
- 业务备份包含数据库一致性快照、该快照引用的托管文件和校验清单；知识目录单独备份，恢复后重建索引。
  启用数据库权威状态前必须具备可验证的备份与恢复，不把它推迟到迁移之后。
- 提供有格式版本的导入导出清单，结构化对象用 JSON/JSONL，正文用 Markdown，附件按文件 ID 关联。

### 7. 权限与助手接入

- 统一的允许/拒绝/待批准入口和审计继续有效，知识私密范围、人的正文、链接和高权限命令保护不放宽。
- Assistant 工具适配器使用正式公开接口并携带明确身份，不直接读写其他模块的表或任意文件。
- 首次接入不把助手默认为 human，也不因“人正在聊天”自动继承全部人类权限。
  知识查询、Work 写入、派活、批准、访问私密等能力分别列出策略，默认沿用当前限制。
  如需新的代办/委托权限，单独提出契约和审批规则。
- 工具可能有副作用，恢复助手轮次时先核查已提交操作；不能简单重放历史工具调用。
- 上下文快照、记忆和检索缓存继承来源的访问限制；查到资料不代表可以向执行器交付全部笔记。
- 模型调用网络留在适配器，业务核心通过注入接口使用。测试用假的模型与工具，不调用真实 agent 或读取真实知识库。

### 8. 契约影响与切换

本 ADR 不修改或生成任何 schema。需要 Claude 起草、人类批准的具体契约至少包括：

| 位置/契约 | 需要表达的变更 |
|---|---|
| `entities.ts` 中 Project/Task/Routine 与 `common.ts` | 从笔记格式分离业务对象、正文版本、讨论与关系；拆开负责人和执行情况；保留旧格式解码 |
| `operation.ts`、`api.ts` | Work 创建/更新/讨论/编辑/显式派活等操作；结果能表达业务对象，不再一律以 NoteRef 表达 |
| `query.ts` | 独立 Work/Execution 查询；知识查询与旧笔记查询的兼容范围；跨模块引用 |
| `job.ts` | 保留现行可靠派活协议，明确来源和输入版本；新增需要升级协议时先规定双方版本兼容与拒绝规则 |
| 新的 Assistant/日志/备份契约 | 对话、轮次、工具记录、格式版本、清单和恢复校验；新增 ID 前缀统一批准 |
| 导出脚本与生成物 | 从批准后的 Zod 自动生成，不能手改 |

- 旧 `v1` 响应保持原格式，不能往 strict 对象静默添加字段或伪造 Markdown 路径。
  新业务对象使用显式版本化接口；版本路径、字段、错误与兼容矩阵在 schema 提案中确定。
- 老客户端不能操作已切换为数据库权威的对象。不能把结构化 Work 对象伪装成仍可写的任务笔记。
  迁移完成前同步升级 Hub/CLI，Runtime 协议变更时也要给出兼容窗口。
- 旧笔记的稳定 ID、历史 Job、轮次、会话和来源路径保留映射；Task/Project/Routine 的未知字段、人的正文与原始字节不丢失。
  `turn` 与对象形式的 assignee 只用于旧数据解码，不重新成为新系统控制开关。
- 跨模块引用使用新对象引用，历史文件链接按清单提供明确的兼容映射或导出视图。
  文件链接无法保留时在 dry-run 报告中逐项列出，切换前解决；不自动重写人的知识链接。
- 备份与 dry-run 都成功后才允许显式切换。切换前暂停受影响对象的派活；有运行中 Job 或待交回结果时拒绝直接切换，
  先完成或明确处理。导入历史不触发执行，不重新发送已经发生的工具调用或审批。
- 使用事务和迁移记录保证中断恢复与重复导入不重复建对象；输入内容版本变化或 ID 冲突时拒绝 apply。
- 原始笔记先完整归档，旧字段只按来源映射保留，不继续双向写回。旧文件退出控制的具体方式由迁移清单明确展示。
  不由 Hub 启动自动迁移真实数据。
- 回退必须先停止新版本，恢复配套数据库与文件快照，再启动对应旧版；有新工作发生后不能直接用旧程序打开新库。
  恢复到备份后的新增数据需要另行导出核对，不承诺无损自动降级。

### 9. 实施与现行规则

- 按 R0-0 的切片逐步实施，每个普通切片只改一个 package/app；确需契约连带修改时显式列出范围。
- 不创建仅有空导出、没有真实调用与测试的业务包作为“完成重构”的依据。
- 新功能有测试，跨边界输入输出用 `@lumio/schema` 校验；依赖隔离、失败恢复、兼容和迁移需有验收。
- 测试只用 `fixtures/` 的合成数据和临时目录；本次工作不读取或迁移真实 vault，不触碰实际已安装服务。
- 未批准前 DESIGN 的现行规则继续生效。本文若分节落地，只把已实现并合并的部分同步为现行设计；旧 Implemented ADR 不改原文。
- 未来将调整 ADR 0001/0007/0012/0014/0019/0023/0024 涉及“所有实体都在 vault”、任务文件控制、写回和自研助手的部分；
  其余依赖边界、可靠执行、隐私与审批原则继续有效。旧 ADR 的取代标记在对应实现合并时处理。

## 后果（好处 / 代价）

- 知识、工作、执行、助手可独立使用和测试，存储格式变化不牵动全部模块。
- Task/Project 的查询、关系、并发编辑与派活可以使用数据库约束和事务。
- Markdown 保留知识写作与外部编辑优势，JSONL 承担过程数据；每类数据的备份责任更明确。
- 需要正式的数据库迁移、正文编辑流程、客户端兼容和数据恢复；任务状态不再能靠同步笔记文件修改。
- 跨模块协调、接口转换和投影增加实现成本，必须限制范围，不能在此次重构中顺带建设完整多用户或模型路由平台。

## 修订记录

- 2026-10-31：人类指令“给我批准并重构，直至最后完成”，批准本提案并授权在其范围内细化必要契约和持续实施；schema 仍由 Claude 起草，保留交叉 review、合成数据测试与现有权限约束。新范围不因本授权自动纳入。
