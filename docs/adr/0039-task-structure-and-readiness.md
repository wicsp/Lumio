# 0039 任务结构与可开工状态：依赖推导、分组约定、AI 可维护

- 状态：Implemented（2026-11-08）
- 日期：2026-11-08
- 领域：数据 | AI 协作与权限
- 影响：契约向后兼容的新增：`WorkTask.blocked_by`（读取时推导）、`WorkTaskDetail.dependents` / `children`、
  `work.task.list` 的 `readiness` / `tag` / `parent` 筛选；改变一条现行规则：已取消或已删除的前置任务不再阻塞（第 3 节）。
  `docs/design/work.md`、`web.md`、`skills/lumio/SKILL.md` 随实现同步修改。
- 实施说明：[T1-0](../tasks/T1-0-task-structure-and-readiness.md)

## 背景

一个系统里常同时挂着十来个改进任务，有些有先后关系，人管不过来，AI 读的时候也只能看到一张平铺的列表。
人类在 2026-11-08 提出：最终希望只和 AI 聊天，由 AI 自动做任务分类、依赖图和安排；同意分两层做——
先让依赖与分组成为系统里显式、可推导、可编辑的数据（本 ADR），AI 自动整理以后建立在这一层之上。

现状（v3 任务模型，ADR 0032）：契约已有 `project`、`parent`、`dependencies`、`tags`；`packages/work` 已校验依赖成环与父任务成环，
前置未完成时拒绝委派、拒绝标记完成。缺的是：

1. 没有「被阻塞」这一推导状态——前置没完成的任务和普通待办混在「你的待办」里，人与 agent 都得逐个打开才知道能不能开工；
2. 列表与能力目录不能按「可开工 / 被阻塞」、标签、父任务筛选，也查不到「谁依赖我」「我的子任务」；
3. Web 只把依赖显示成原始 ID，不能编辑依赖、父任务和标签；
4. 前置被删除或取消后，后续任务永远无法委派或完成（`task()` 对回收站对象抛 NOT_FOUND，`outcome` 永远不是 done）。

## 决定

### 1. 结构只有三种，不新增实体

- **项目**（`project`，至多一个）：回答「为了哪个目标」。
- **父任务**（`parent`）：大块工作拆成子任务时使用，承担 epic / 里程碑的角色。**不新增 milestone、epic、分类等实体或字段。**
- **标签**（`tags`）：自由文本，用于横向分类（如 `ui`、`infra`、`paper`）。标签主要由 AI 维护，人不需要维护一套分类体系。
- **依赖**（`dependencies`）：「这个任务要等这些任务完成才能开工」，是唯一的先后关系。父子关系不隐含依赖。

### 2. 可开工状态是推导出来的，不存储

- `blocked_by` = `dependencies` 中**结局为 open** 的任务 ID（保持 `dependencies` 的顺序）。读取任务（列表、详情、能力结果）时由 Work 推导填入；
  不写入数据库，不出现在任何 patch / create 参数中，客户端提交会被严格对象拒绝。缺失与 `[]` 等价，都表示不被阻塞（ADR 0008）。
- **被阻塞** = 结局 open 且 `blocked_by` 非空。被阻塞不是新的 turn 原因，也不改变「轮到谁」：它是叠加在 turn 上的事实。
  被阻塞的任务不能委派（现有规则，错误信息里带上 `blocked_by`），界面另行分组显示。
- 「需要你处理」（attention）与通知不变：被阻塞不触发通知，前置完成使任务解锁也**不**通知、不自动委派（自动安排属于第二层，见第 5 节）。

### 3. 已取消或删除的前置不再阻塞

- 前置任务结局为 `cancelled`，或已移入回收站 / 彻底删除时，**不计入 `blocked_by`**，不阻止委派和完成。
  该 ID 仍保留在 `dependencies` 里（不级联修改，ADR 0038），恢复回收站后若结局为 open 则重新计入。
- 界面在依赖列表里把这类前置标成「已取消」「已删除」，由人决定是否移除这条依赖。
- 理由：前置被放弃时，后续任务是否还成立只有人能判断；永久卡死比放行更糟，而放行后人仍能在界面上看到提示。

### 4. 读取与筛选

- `WorkTaskDetail` 新增 `dependents`（依赖本任务、未在回收站的任务 ID）与 `children`（父任务为本任务的 ID），都是推导字段。
- `work.task.list` 新增可选筛选：`readiness: "ready" | "blocked"`（`ready` = 结局 open 且不被阻塞）、`tag`、`parent`。
  CLI 对应 `lumio task list --ready / --blocked / --tag / --parent`。
- agent 能力目录的 `work.task.list` / `work.task.show` 说明里写明这些字段，SKILL.md 说明「先看 `--ready`」。

### 5. AI 维护结构的边界（为第二层预留，本期不实现自动整理）

- 修改 `project`、`parent`、`dependencies`、`tags` 仍走现有 `work.task.update`：人直接改；内置助手与外部 agent 按现有权限与提议规则（ADR 0029、0032）执行，
  不为结构修改另设通道。
- 以后的「AI 自动分类、建依赖、排计划」只能通过这些命令产生变化，因此天然留有交接记录、版本与可撤回的提议；
  是否允许某类结构修改免批准，由以后的对话式授权决定，不在本 ADR 范围。

## 后果

- 好处：人和 agent 都能一眼看到「现在能开工的是哪些」；依赖图成为所有 agent 共享的事实，而不是每次对话里临时推理；
  第二层（AI 自动整理）不需要新的数据模型。
- 代价：任务读取要多查一次前置结局（单机 SQLite，规模在几百到几千个任务，可接受；列表一次性批量查询）；
  `WorkTask` 出现一个只读推导字段，存储层写入前要剔除它，契约测试要覆盖「提交带 `blocked_by` 被拒绝」。
- 否决的方案：
  - 把「被阻塞」做成 turn 原因 `blocked`：会和「轮到谁」纠缠（被阻塞时到底轮到谁？），且前置完成时要批量改写别的任务的 turn 与交接记录。
  - 新增 milestone / 分类实体：父任务与标签已经够用，多一层实体只会让人更难管，也让 AI 多一种要决定的东西。
  - 完全不存结构、只让 AI 在对话里推理：不同 agent、不同对话会得出不同结论，也无法做「可开工」的确定性判断。
