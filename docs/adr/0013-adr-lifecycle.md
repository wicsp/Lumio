# 0013 ADR 的生命周期：实现之后才定稿

- 状态：Implemented（2026-10-25）
- 日期：2026-10-25

## 背景
原来的状态只有 Proposed、Accepted、Superseded，默认 Accepted 之后就不再修改。实际上，很多 ADR 在接受之后、
动手实现之前，都因为新的认识被修改过（例如 0004 改了三次、0012 补充了卡号防护），规则与实际做法不一致。
真正需要冻结的不是"决定"，而是"已经写进代码的决定"：代码、测试和其他文档都依赖它，改了会悄悄失效。

## 决定

### 1. 四个状态
| 状态 | 含义 | 能否修改原文 |
|---|---|---|
| `Proposed` | 起草中，等人类批准 | 可以随意修改 |
| `Accepted` | 人类已批准，**还没有实现** | 可以修改，但每次修改都要人类批准，并记入"修订记录" |
| `Implemented` | 已经实现（代码合并到 `main`） | **定稿**，不再修改；要变更就写新的 ADR |
| `Superseded by NNNN` | 被新的 ADR 取代 | 不再修改 |

### 2. 部分实现
一条 ADR 的各个小节可以分批实现。此时状态写成：

```
- 状态：Accepted（部分实现：第 1、2 节已实现）
```

**已实现的小节视同定稿**，不再修改；其余小节按 Accepted 的规则处理。全部实现后，状态改为 `Implemented`。

### 3. 定稿之后怎么改
- 写一条新的 ADR，说明改什么、为什么改；新 ADR 实现后，旧 ADR 改为 `Superseded by NNNN`
  （只是部分被取代时，写"第 N 节被 NNNN 取代"）。
- 唯一允许直接改原文的情况：错别字、失效的链接、明显的笔误，且不改变任何含义。

### 4. 修订记录
`Accepted` 状态下的每次修改，在文末"修订记录"一节加一行：日期、改了什么、谁批准的。
状态行和日期行只写当前状态与最初的日期，不再在括号里堆叠修订说明。

### 5. 谁来改状态
- `Proposed → Accepted`：人类批准时。
- `Accepted → Implemented`（含部分实现）：实现该 ADR 的 PR 合并时，由合并的人或 review 的一方在同一个 PR 里修改。
- 每条任务说明（`docs/tasks/`）列出它实现了哪些 ADR 的哪些小节，作为改状态的依据。

## 后果
- 好处：规则与实际做法一致；已经写进代码的决定不会被悄悄改掉；每条 ADR 的演变过程有记录可查。
- 代价：状态行更长；PR 合并时要多做一步"更新 ADR 状态"。
