# 0036 只为架构级决定写 ADR；现行设计拆成总览加分册

- 状态：Implemented（2026-11-06）
- 日期：2026-11-06
- 领域：流程
- 影响：修订 ADR 0015 第 1、2 节（"DESIGN.md 是唯一说明"改为"总览加分册"，"每条规则注明出处 ADR"放宽为可以标任务或 PR）；
  ADR 0015 第 3 节（改 ADR 必须同步改设计文档）不变，ADR 0013 不变；`docs/DESIGN.md`、新增 `docs/design/`、`AGENTS.md`、`docs/README.md`、`docs/tasks/README.md`、
  `docs/adr/0000-template.md`；`apps/hub` 中 vault 说明文件里指向目录结构的链接。

## 背景

2026-10-25 到 2026-11-06 的不到两周里写了 34 条 ADR。规则只规定了"改契约必须先写 ADR"和"改 ADR 必须同步改 DESIGN"，
没有规定什么时候**不必**写 ADR，于是一部分小改动也写成了 ADR（例如 0023 补全时写出开关字段、0028 界面语言与主题切换），
每条都要走 Proposed → Accepted → 修订记录 → 部分实现 → Implemented，并同步改 DESIGN。

同时 `docs/DESIGN.md` 长到约 50 KB、411 行。ADR 0015 当初正是因为"AI 每次读全部 ADR 约 5 万字节"才设立 DESIGN.md，
并预见了代价："DESIGN.md 需要保持精炼，不能慢慢长成第二套 ADR"。这件事已经发生：DESIGN 里混进了界面交互细节、完整命令表和阶段进度，
AI 每次开工都要读全部 50 KB，大部分与手头任务无关。

人类在 2026-11-06 的对话中指出"加个按钮也要写 ADR 吗"，并批准本方案。

## 决定

### 1. 什么时候写 ADR

只有**架构级决定**写 ADR：

- 改 `packages/schema` 契约或 Hub/Runtime 协议（AGENTS.md 硬规则第 1 条不变）；
- 改模块边界或依赖方向；
- 改权限、身份或安全模型；
- 改存储格式、存储权威，或需要迁移数据；
- 改发布包格式、安装布局或升级兼容；
- 认真比较并否决过有分量的备选方案，以后很可能有人再提。

拿不准时问两个问题：**半年后会不会有人问"当初为什么不用另一种做法"？改回来需不需要迁移数据或改契约？**
两个都是"否"，就不写 ADR。仍拿不准时由 Claude 在对话里问人类。

### 2. 不写 ADR 的改动写到哪里

| 改动 | 例子 | 写到哪里 |
|---|---|---|
| 不改变任何规则 | 加按钮、改样式、修 bug、模块内部重构、改文案 | 任务说明或 PR 描述；设计文档不动 |
| 改变现行规则，但没有争议 | 调整默认值、新增命令选项、补一条边界检查 | 直接改设计文档，在规则后标任务或 PR 编号 |
| 架构级决定 | 见第 1 节 | 写 ADR，并在同一个 PR 里改设计文档（ADR 0015） |

具体功能需求（界面怎么排、命令有哪些选项、验收步骤）写在 `docs/tasks/` 的任务说明里；任务说明做完后保留原文，不需要像 ADR 那样维护状态。

### 3. 现行设计拆成总览加分册

- `docs/DESIGN.md` 只保留总览：目标、总体结构、工程基础（含模块依赖表）、存储权威与备份、流程，以及分册索引和旧节号对照。
- 各模块的规则放到 `docs/design/` 下：`knowledge.md`、`work.md`、`execution.md`、`assistant.md`，
  以及跨模块的 `hub.md`（Hub 职责、存放、部署、迁移）、`web.md`、`security.md`（AI 协作、权限与安全）。
- 总览加分册共同构成"现行设计"，取代 ADR 0015 第 1 节中"DESIGN.md 是唯一说明"。
- **AI 开工时读 `AGENTS.md`、`docs/DESIGN.md`、自己的任务说明，以及任务说明里列出的分册**，取代 ADR 0015 第 2 节。
  任务说明须在"依据"里列出要读的分册。
- 不按 ADR 分文件夹、不改 ADR 编号与路径；已有 ADR 不回溯合并或删除。

### 4. 设计文档写什么、多长

- 只写规则、不变量和模块边界。不写界面交互细节、完整命令表（以 `--help` 和代码为准）、实现步骤和阶段进度。
- 阶段表移到 `docs/tasks/README.md`。
- **体积上限**：`DESIGN.md` 和每个分册各不超过 15 KB。超出说明混进了功能细节，在造成超出的 PR 里精简；做不到时告诉人类。
- 规则后的出处可以是 ADR、任务编号或 PR 编号。

### 5. 本次拆分的范围

规则原文搬到分册，章节标题去掉编号，交叉引用改成分册链接；并按第 4 节删去已混入的界面细节，不改变规则：

- `web.md`：页面清单、快捷键、设置页布局、窄屏导航改为指向 `apps/web/README.md`；保留其中的数据与安全规则。
  同时更正两处与现行实现不一致的旧说法：界面已不是"中文 GUI"；推送上线后已注册只处理推送的 `/sw.js`（R4-5）。
- `work.md`：Web 任务页的界面描述删去（`/sw.js` 规则移到 `web.md`）；CLI 命令全表改为以 `--help` 为准。
- `execution.md`：Routine 的 CLI 命令全表改为以 `--help` 为准。
- `DESIGN.md` 的终端输出：只保留着色开关与退出码规则，删去符号与颜色的具体样式。
- 拆分期间合并的 #99（ADR 0034、0035）对旧 DESIGN 的修改按同样原则归位：规则进 `design/knowledge.md` 与 `design/web.md`，
  界面细节（自动保存间隔、推荐区布局、`【【` 触发、脚注浮层等）进 `apps/web/README.md`。
- `docs/README.md` 的 ADR 索引补上此前漏登的 0029–0035。

## 后果

- 好处：小改动不再走 ADR 流程；AI 每次读的设计文档从约 50 KB 降到总览约 14 KB 加相关分册；
  分册有体积上限，不会再长成第二套 ADR。
- 代价：没有 ADR 的规则只能从任务说明或 PR 里找原因；"要不要写 ADR"多了一次判断；
  2026-11-06 之前的 ADR 与任务说明按旧节号引用 DESIGN，需要经 `DESIGN.md` 末尾的对照表查找。
