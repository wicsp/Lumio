# 0015 文档结构：DESIGN.md 写现行规则，ADR 只记原因；ADR 按领域打标签

- 状态：Implemented（2026-10-25）
- 日期：2026-10-25
- 领域：流程

## 背景
现行规则散落在十几条 ADR 里，不少规则改过多次，要把几条 ADR 叠起来读才能拼出当前版本。
AI 每次开工都读全部 ADR（约 5 万字节），既占上下文，又容易把被推翻的旧说法当成现行规则。
原来的 `ARCHITECTURE.md` 本应承担"现行设计"的角色，但太单薄，规则还是要回 ADR 里找。

ADR 和设计文档回答的是两个不同的问题：ADR 回答"为什么这样决定"，应当保留历史；
设计文档回答"现在是什么样"，应当随时改成最新状态、不保留历史。

## 决定
1. **`docs/DESIGN.md` 是现行设计与规则的唯一说明**，按领域组织，只写现在生效的内容，每条规则注明出处 ADR。
   它取代原来的 `docs/ARCHITECTURE.md`（已删除，内容并入）。
2. **AI 默认只读 `AGENTS.md`、`docs/DESIGN.md` 和自己的任务说明**；需要了解某条规则的原因时，才去读对应的 ADR。
3. **同步规则**：新增或修改 ADR 的 PR，必须在同一个 PR 里同步修改 `DESIGN.md`。两者不一致时，
   说明有一方没同步，发现的人（或 AI）应告诉人类，而不是自行选择相信哪一份。
4. **ADR 按领域打标签**：在状态、日期之后加一行 `- 领域：…`，一条 ADR 可以有多个领域。
   不按领域分文件夹：大多数 ADR 横跨多个领域，而且编号和路径已被代码与文档引用。
   当前的领域：工程基础、数据、Hub 与运行、AI 协作与权限、安全、流程；以后需要时可以新增（例如"界面"）。
   给已有 ADR 补"领域"一行不改变其内容，`Implemented` 的 ADR 也可以补。
5. **未实现的 ADR 可以按主题合并**（ADR 0013 允许修改 `Accepted` 的内容）：合并后删除原文件，
   在新 ADR 中注明"合并自"，并更新所有引用。本次将 0006、0010、0011 合并为 0014。

## 后果
- 好处：AI 每次读的内容少且都是现行规则；ADR 仍完整保留原因；按领域能快速找到相关决定。
- 代价：每次改 ADR 要同时改两份文档；`DESIGN.md` 需要保持精炼，不能慢慢长成第二套 ADR。
