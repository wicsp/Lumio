# 0031 任务流程与 agent 接力、委派需要批准、统一推送（先做 PWA）

- 状态：Accepted（2026-11-04 人类在对话中审阅并批准）
- 日期：2026-11-04
- 领域：AI 协作与权限 | Hub 与运行 | 客户端 | 流程
- 影响：修订 ADR 0019、0029 第 3 节（agent 委派由「拒绝」改为「需要批准」）；补充 ADR 0030（流程中的人类步骤复用提问与验收）；
  术语「派活」改为「委派」（DESIGN、任务说明、界面与命令行文字）；新增 `packages/schema` 契约（流程、推送订阅），由 R4-1 起草。
- 实施说明：[R4-0](../tasks/R4-0-workflows-delegation-push.md)

## 背景

作者想把现在的开发方式放进 Lumio 本身：在一个对话里和 Claude 讨论设计，Claude 用 Lumio skill 建任务并写好说明，
交给 Mac 上的 Codex 实现；Codex 做完交给 Claude review；Claude 问作者是否合并；作者同意后 Claude 合并；最后作者验收并标记完成。

对照 ADR 0029、0030，缺三样：

1. agent 不能委派（ADR 0029 一律拒绝），Claude 建好任务后只能等人手动派出；
2. 一轮结束后总是回到人手上，agent 之间不能按预定顺序接力；
3. 「等你回答 / 等你验收」只显示在页面上，人不打开就不知道。

另外，作者认为「派活」不够正式，文档与界面要换一个说法。

## 决定

### 1. 术语：「派活」改为「委派」
- 中文：把任务的一轮交给某个 agent 执行，统一叫**委派**（「委派给 codex@mac」「委派下一轮」「回答并继续」不变）。英文仍用 dispatch。
- 契约与命令名不改（`work.task.dispatch`、`lumio task continue`）；改的是文档、界面与命令行输出里给人看的文字。旧 ADR 的正文按 ADR 0013 不改，
  在 DESIGN 与新文字中使用新术语。

### 2. agent 委派：需要人批准
- agent 发起 `work.task.dispatch`（包括带 `comment` 的）不再直接拒绝，而是走授权的第三种结果**需要批准**：生成一条提议，
  提议里是完整的委派命令（任务、目标 agent、看到的 revision）。
- 人在「需要你处理」里看到「Claude 想把『…』委派给 codex@mac」，一键批准即执行；拒绝则不执行。提议过期或任务 revision 已变时批准失败并说明。
- 完成、取消、例行任务、决定提议、高权限命令、删除归档仍然对 agent 一律拒绝（ADR 0029 第 3 节其余不变）。

### 3. 任务流程：批准一次，agent 步骤自动接力
- 任务可以带一个**流程**：有序的步骤列表。每步是以下两种之一：
  - **agent 步骤**：执行者（如 `codex@mac`）与这一步要做的事（说明文字）；
  - **人的步骤**：提问（如「是否合并？」，答案决定下一步）或验收（标记完成）。
- 步骤之间的走向：默认按顺序；agent 步骤可以声明「打回」去向（例如 review 认为需要修改时回到实现步骤），
  agent 在汇报里用 `<lumio-outcome>changes</lumio-outcome>` 表示打回，否则视为通过。人的提问步骤按回答选择去向。
- **批准**：流程由人建立即生效；由 agent 提出的流程是一条提议，人批准后生效。批准的是整个流程（步骤、执行者、轮数上限），
  之后 agent 步骤之间自动委派，不再逐次批准；遇到人的步骤就停下，进入「需要你处理」（复用 ADR 0030 的提问与验收）。
- **保护**：每个流程有轮数上限（默认 8）；达到上限、某一步失败或结果不明时停下来交给人。人随时可以暂停任务，流程随之停止。
  流程只能委派给流程里写明的执行者；修改已批准的流程需要重新批准。
- **上下文**：流程不依赖某个对话。每一步的输入是任务描述、这一步的说明、此前各轮的汇报与讨论（与现有续轮一致），
  因此讨论设计的结论应写进任务描述（如 ADR 与实现说明）。review 等步骤交给执行器上的 agent（如 `claude-code@mac`），不回到 claude.ai 的原对话。
- 流程模板：常用流程可以保存为模板（如「实现 → review → 人决定合并 → 合并 → 人验收」），新建任务时套用。

### 4. 推送：统一接口，先做 PWA
- Hub 内部定义统一的通知接口：一个事件（谁、什么事、跳转到哪里）交给已启用的各个通道发送；通道是可插拔的，
  先实现 **Web Push（PWA）**，以后加飞书等。
- 触发通知的事件：需要你处理的新条目（等你回答、等你验收、执行失败）、待批准的提议（包括 agent 委派与流程）。
  通知正文只含任务标题与事件类型，不含汇报、问题原文或私密内容；点击打开对应页面。
- Web Push 要求：页面通过 **HTTPS** 访问（Tailscale 的 HTTPS 地址或 README 的 Caddy 反向代理）；iOS/iPadOS 16.4 及以上、从主屏幕图标打开；
  开启通知必须由用户点击触发。Hub 生成并私密保存 VAPID 密钥，需要能访问浏览器厂商的推送服务。
- 设置页增加「通知」：开启 / 关闭本设备的通知、发送测试通知、按事件类型开关。每台设备一个订阅，可在设置里移除。
- 加密与签名（RFC 8291、RFC 8292）优先用运行时自带的加密接口实现，不引入依赖；若实现者认为必须引入依赖，按 AGENTS.md 在 PR 中说明理由与替代方案，由人决定。

### 5. 不在本 ADR
- **按对话语义授权**（作者在对话里明确授予 agent 某项权限后，Hub 据此动态放行）：作者计划的下一步，另写 ADR。
  届时需要回答：授权意图如何确认来自人本人而不是对话里引用的内容（提示注入），授权的范围与时效，以及如何在审计里留下依据。
- 飞书等其他推送通道；原生 App。

## 后果

- 好处：作者现在「讨论 → 写说明 → 交给 Codex → review → 决定合并 → 验收」的做法可以完整放进 Lumio；
  agent 能主动推进，但每个需要人拍板的点都停下来并通知到人。
- 代价：流程引擎（步骤走向、轮数上限、打回）与推送（订阅、密钥、加密）是新的复杂度；Web Push 依赖 HTTPS 部署与推送服务的可达性。
- 风险：agent 用自己的外部凭据（如 GitHub）做的事 Lumio 管不住，例如在提问之前就合并。应在外部系统限制凭据权限
  （实现者的令牌不能合并，只有合并步骤使用有合并权限的凭据，必要时加分支保护）。
