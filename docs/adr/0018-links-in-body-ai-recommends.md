# 0018 链接写在正文里，AI 只推荐不写链接，`related` 弃用

- 状态：Accepted
- 日期：2026-10-25
- 领域：数据、AI 协作与权限
- 影响：ADR 0014 第 1、4 节，ADR 0016 第 3 节的 P1 规则表，`packages/schema` 中 `Base.related` 的说明

## 背景
ADR 0014 的设计是：AI 提议在 frontmatter 的 `related` 中加链接，人接受后由 Hub 写入。P1-4 按此实现。
走查设计时人类指出几个问题：
1. **链接的价值在上下文。**"这两篇有关"没有用，"这里的防御思路和 [[X]] 一样，只是换到了协议层"才有用。
   只有正文里那句话能说明链接的意义，`related` 说明不了。
2. **幽灵链接。** 不在写作当下处理的链接，以后永远不会处理。即使每条都经过批准，批准时也只是点了"接受"，
   没有把它写进自己的思考里。
3. **`related` 是多余的。** 索引本来就从正文解析 `[[ ]]`，链接图可以完全由正文得出。
4. `related` 里存 ID，Obsidian 只当作普通文字：点不了，关系图里也看不到。

## 决定
1. **链接只写在正文里**，用标准的 `[[文件名]]`（可带 `|别名`、`#标题`），由人在写作时写，并在句子里说明关系。
2. **AI 只推荐，不写链接。** AI 检索已有笔记，在对话中告诉人"哪篇笔记的哪一段和这里相似"，并给出原文。
   用不用、怎么写进正文由人决定。AI 若要把推荐写进文件，只能写在 AI 区块里（区块内的链接本来就不计入人的链接图）。
   Hub 的规则表中，`agent` 请求 `link.add` 一律**拒绝**（`agent-cannot-write-links`）。
3. **`related` 弃用。** 仍保留在契约中，已有的值照常解析进链接图，避免旧笔记报错；Lumio 不再写它，也不建议人写。
   `lumio link add`（human 的 `link.add`）暂时保留，作为操作与审批流程的样例；P2 引入第一个真实的写操作时，
   与 `related` 一起删除。
4. **改名只在受控环境里进行**：Obsidian（需打开"自动更新内部链接"）或以后自己的客户端（经 Hub 的改名操作，
   同时更新引用）。在访达、"文件" App、AI 直接 `mv`、git 回退等方式改名会造成断链，Lumio **只负责发现**：
   列出所有悬空链接，不自动修复。
5. **导出时从正文找引用。** `lumio export bib --from <笔记>` 只导出这篇笔记正文里引用到的论文
   （`[[citekey]]` 或 `\cite{citekey}`），而不是整个论文库。
6. 操作、提议、授权、审计的框架（ADR 0016）保留，等 P2 有真正需要批准的操作时使用。P1 中没有需要批准的操作。

## 后果
- 好处：每条链接都有上下文；没有幽灵链接；Obsidian 里能点击、关系图可见；少维护一个字段；
  P1 不再需要人处理提议队列。
- 代价：按文件名的链接在受控环境之外改名会断（只能发现，不能防止）；AI 无法替人建立链接，
  发现关系的价值要靠人把推荐写进正文；`related` 和 `link.add` 暂时作为弃用代码留在仓库里。
