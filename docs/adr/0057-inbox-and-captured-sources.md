# 0057 Inbox 与外部资料入库：原文、AI 卡片、检索与关联建议

- 状态：Accepted
- 日期：2026-11-11
- 领域：数据、AI 协作与权限、安全、Hub 与运行
- 相关：ADR 0005（job/attempt）、0012（source 类型）、0018（AI 只推荐不写链接）、0025（四模块）、0035（相关推荐）、
  0038（回收站）、0041（AI 配置底座）、0051（AI 笔记与来源）、0053（AI 笔记文件名）、0055（语音）；任务 I1-0

## 背景

人每天会遇到不少文章、论文、视频。有的当场看完，有的想以后看，有的不打算看、只想留给 AI 当资料，
还有的本来想看、后来忘了。他希望遇到时一键存下来，Lumio 按类型解析、留住原文、让 AI 先写一份总结；
以后提到相关的事情时，AI 能把这些资料找出来、推荐给他或者和当前的事联系起来。

2026-11-11 的讨论中人类关心几件事：原文要不要全存、成本多少；要不要一存下就总结；用 RAG 匹配的计算和存储成本；
以及这些资料、AI 写的内容、他自己写的笔记之间的链接该怎么建立。按个人用量（约每天 10 条、一年约 3650 条）估算：

| 项目 | 量级 |
|---|---|
| 原文文本（文章正文、论文 Markdown、视频字幕） | 每条 10–150 KB，一年不到 0.5 GB |
| 论文 PDF | 每篇 1–5 MB，按每天一篇算一年约 1 GB |
| 入库时的 AI 卡片（每条输入截断到约 5–10k token） | 一年约 3–4 千万输入 token，用国产模型约一两百元 |
| 卡片向量（每条一个，1024 维） | 一年约 15 MB，几千条暴力计算余弦相似度是毫秒级 |

结论是钱不是瓶颈。真正要防的是三件事：资料变成噪音；AI 写的内容混进人的知识；关联在错误的时机或以错误的方式出现。

同时讨论了模块归属：外部资料（论文和其他资料）本来就是知识，属于 Knowledge；Inbox 不只收资料
（以后语音里提到的想法、待办也会先进 Inbox），所以它是跨模块的收件入口，不是第五个业务模块。
"Resource"一词已用于 ADR 0051 的资源锚点，外部资料沿用 ADR 0012 的 `source`（以及 `paper`）。

## 决定

### 1. 三层内容，各有归属

每条入库的资料由三部分组成：

| 层 | 内容 | 写入者 | 位置 | 性质 |
|---|---|---|---|---|
| 原文层 | 抽出的正文、论文 Markdown、视频字幕；论文 PDF | Lumio | 文本在 vault 的 `files/originals/`；PDF 在 Hub 托管文件 | 只读，长期保留；AI 层可从它重新生成 |
| AI 层 | 卡片与深读总结 | AI | `ai/notes/` 的一份 AI 笔记（ADR 0051） | 可重新生成，标明 AI 写 |
| 人的层 | 笔记、正文里的链接、状态 | 人 | `library/papers/`、`library/sources/` 的实体文件 | 最宝贵，AI 不能改 |

- **实体**：论文入库为 `paper`（沿用 citekey 与去重规则，ADR 0004），其他为 `source`（`kind` 取 `web` / `video` / `podcast` 等）。
  实体正文是原有模板，开头单独一段嵌入它的 AI 笔记（ADR 0051 第 4 节的写法），其余留给人写。
- **原文文件**：`files/originals/<标题> <实体 ID>.md`（文件名规则同 ADR 0053，改标题不改文件名）。
  frontmatter 记录 `of`（实体 ID）、`url`、`captured`、`extractor`（抽取方式与版本）、`lang`、`sha256`；正文是抽出的 Markdown。
  `files/` 不扫描为实体（ADR 0012），因此原文不会变成"笔记"，也不进链接图。
- **原文只读**：Web 中不可编辑；人要求"重新抽取"时整体替换，旧版本留在 vault 的 git 历史里。
- **二进制原件不进 vault**：论文 PDF 存为 Hub 托管文件（ADR 0025），随业务备份；原文文件的 frontmatter 记录它的文件 ID。
  理由是 vault 会被 git 自动提交并被外部同步，每年上 GB 的 PDF 会让两者都变重。网页图片不下载，保留原地址；视频与音频本身不保存，只存链接和字幕。

### 2. Inbox：跨模块的收件入口

- **捕获记录**（Capture，ID 前缀 `cap`）存在 `hub.sqlite`，和提议、审计一样属于 Hub 的跨模块协调数据。
  它记录：输入（URL 或文本）、来源渠道、处理状态、产生的实体 ID、错误，以及**是否已分拣**。
- **Inbox 就是"未分拣的捕获"**：分拣（想读 / 存档 / 已读 / 丢弃）之后就离开 Inbox。阅读状态写在实体 frontmatter 里，
  Inbox 本身不复制知识内容。
- **未分拣也能被检索**：解析成功就生成实体与原文，"不看、只留给 AI"的资料不需要人再做任何事。
- **阅读状态**：`paper` 与 `source` 的 `status` 增加 `reference`（存档：不打算读，留作资料）。
  入库默认 `to-read`。"想读但后来忘了"不是一个状态，由入库时间与是否打开过推导；不定时提醒。
- **丢弃**：把实体与原文移入回收站（ADR 0038）；AI 笔记一并移入。捕获记录保留，同一 URL 再次捕获时提示曾经丢弃过。
- **去重**：URL 规范化（去掉跟踪参数、统一 arXiv/DOI 形式）后相同即为重复，返回已有实体，不重复解析。
- 第一版 Inbox 只收资料；语音里的想法、待办以后另定，届时复用同一捕获记录。

### 3. 解析：内容从哪里来（2026-11-11 修订）

按"人手上有什么"分三条路径：

| 情况 | 谁拿内容 | 说明 |
|---|---|---|
| 人正在浏览器里看（网页、视频字幕、PDF） | **浏览器插件直接送给 Hub**（主路径） | 人看得到就一定有访问权限：登录、付费墙、代理都不成问题；Hub 不需要再联网 |
| 只有链接（手机分享、粘贴、命令行） | **Hub 下载** | 网页正文、arXiv HTML 与元数据；Hub 按服务配置的代理联网（第 7 节） |
| 视频没有字幕，需要转写 | **派给执行器** | 下载音频后语音识别；只派认识的视频平台 |

- **插件直接连 Hub**，和 Web 一样是人的入口，配对后带自己的令牌调用捕获接口；不经过执行器转发。
  插件在视频页面取出页面已有的字幕一起送来；打开的 PDF 直接把文件送来。
- **Hub 下载**沿用 K1-3 受限抓取的做法，只做轻量抽取。
- **重的处理作为 Job 交给执行器**（ADR 0005、0025）：以 command 类型的 Job 运行执行器上登记过的程序，结果作为托管文件交回，由 Hub 写入原文。不新增 Job 协议。
  - 只把**认识的视频平台**（YouTube、B 站等，列表写在 Hub 中）的链接派给执行器。执行器上的下载工具自己联网，Lumio 无法在其中检查地址，所以任意链接不派出去。
  - 执行器联网用它所在机器自己的代理设置。需要登录的 Cookie 只放在执行器机器上，不进入 Hub。
  - 语音识别在执行器上本地运行，或者把音频交回 Hub，用已配置的云端服务（ADR 0055 的语音 Profile），由人在设置里选。
  - PDF 转 Markdown 先在 Hub 做简单抽取；效果不够时再交给执行器。
- 每条捕获按 job/attempt 记录处理过程；**失败不自动重试**，在 Inbox 中显示原因，由人点"重试"或手动粘贴正文。

### 4. AI 卡片：入库时做；深读：按需做

- **卡片**：解析成功后立即生成，写入该资料的 AI 笔记（`derived_from` 指向实体与原文）。
  内容：一句话说清是什么、3–5 条要点、类型；关键词与人名、方法名等实体作为 AI 笔记的 `tags`。默认用中文写。
  输入有上限：论文取摘要、引言与结论，长文和长视频截断到配置的 token 上限（默认约 8k）。
- **深读总结**：只在人要求时（"让 AI 细读"按钮或对话中提出）生成，用全文更新同一份 AI 笔记，ID 不变（ADR 0051）。
- **写入者**：由 Hub 内置的 Inbox 处理身份（角色 `agent`）写 AI 笔记，审计中可查；它不调用任何工具，只读原文、只写这一份 AI 笔记。
- **模型**：AI 用途绑定增加 `knowledge.summary`（写卡片与深读）与 `knowledge.embedding`（向量），
  沿用 Connection / Profile 底座与用量记录（ADR 0041、0052）。没有配置时，资料照常入库，只是没有卡片和向量；配置后可以补做。
- **外部内容不可信**：原文是第三方写的，可能含有针对 AI 的指令。生成卡片时把原文作为数据放在明确的边界内，
  并且这个调用没有工具；Assistant 检索到原文或卡片时同样作为资料呈现，不当作指令。

### 5. 检索：两级，先卡片后原文

- **全文检索**：原文正文进入知识索引的单独全文表，搜索结果指向所属实体并标明"命中原文"（ADR 0014 的 FTS 规则不变）。
- **语义检索**：每条资料用"标题 + 卡片"生成一个向量，存入 `index.sqlite`（派生数据，可重建；换向量模型时整体重算）。
  人写的笔记与 AI 笔记同样按标题与正文生成向量。几千条的规模直接计算余弦相似度，不引入向量数据库。
- **混合排序**：全文与向量结果按排名融合（RRF）。`knowledge.search` 与编辑器的相关推荐（ADR 0035）改用混合检索，
  结果附带类型、阅读状态与入库时间，供 AI 判断"这是你一个月前想读的"。
- **分块级检索**（在原文里找具体段落）不在第一版，等卡片级检索不够用时再做。
- 私密实体（`life/`）不生成向量、不送去任何模型。

### 6. 两种关系：人写的链接与 AI 算的关联

- **显式链接**：人写在正文里的链接，表达他认可的关系，是知识图谱里唯一的边（ADR 0018 不变）。
- **隐式关联**：由检索实时算出，**不持久化、不写进任何人的笔记**，也不进知识图谱。出现在三个地方：
  - Inbox 中每条新资料旁显示"可能相关"的前 3 条已有知识，附命中片段；
  - 编辑笔记时的相关推荐；
  - Assistant 对话中，AI 按需调用检索，把资料作为参考提给人，并说明为什么相关。
- **采纳**：人认为有关时，自己把链接写进正文（编辑器可以在光标处插入链接，但写不写、写在哪句话里由人决定）。
  采纳后就是显式链接。不维护"已采纳 / 已忽略"列表，也不预先计算所有资料两两之间的关联。

### 7. 权限

- 第一版捕获、分拣、重试、重新抽取、丢弃只对 human 开放。agent 代为捕获以后另定。
- agent 可以读原文（新增只读能力，与读笔记同级，私密规则不变）与 AI 笔记，可以调用混合检索；
  agent 仍只能写 AI 笔记（ADR 0051），不能改实体、原文和人写的链接。
- Hub 抓取网页只允许 `http`/`https` 的公网地址，每次重定向重新检查，限制大小与时间，不带任何 Cookie：
  - **没有配置代理**：解析域名后拒绝回环、内网与链路本地地址，并连接检查过的那个地址。
  - **配置了代理**（Hub 服务环境中的 `HTTPS_PROXY` / `HTTP_PROXY`，遵守 `NO_PROXY`）：请求交给代理，域名由代理解析；
    Hub 只检查网址本身（IP 直接写成非公网地址、`localhost`、`.local` 等一律拒绝）。代理是部署者自己配置的，视为可信。
  - Lumio 不读取、不管理系统代理设置，也不猜测代理的假地址段（fake-ip 的地址段因软件和配置而异）。
    因"非公网地址"被拒绝时，提示里说明：用了代理的话，在 Hub 配置中设置 `HTTPS_PROXY`。
- 设置页写明资料内容会发送给哪个摘要与向量服务（同 ADR 0055 对第三方服务的要求）。

## 后果（好处 / 代价）

- 好处：
  - 存下来几乎不花人的力气；不看的资料也能在以后被找出来。
  - 原文、AI 写的、人写的三者在文件层面分开，AI 层随模型变好可以整层重做；人的知识图谱不被 AI 的关联污染。
  - 成本可控：每条只做一次解析和一张卡片，深读与分块检索按需。
  - 不新增业务模块，不新增 Job 协议，向量不需要单独的服务。
- 代价：
  - 契约变更：`cap` 前缀与捕获、Inbox 接口；`paper`、`source` 的 `status` 增加 `reference`；原文文件格式与 `files/originals/` 路径；
    两个新的 AI 用途绑定；原文读取能力；搜索结果的命中位置与排序字段。
  - 网页正文抽取需要新依赖（在 I1 任务中说明理由与替代方案）。
  - 抓取任意网址引入 SSRF 风险，靠第 7 节的地址检查约束。
  - 隐式关联每次实时计算，没有"以前推荐过什么"的记录；以后需要时另议。
- 否决的方案：
  - **Inbox 与外部资料各成一个模块**：资料与笔记之间的链接会变成跨模块引用；Inbox 本身不拥有知识内容。
  - **一存下就做深度总结**：大部分资料永远不会细看，按需做省掉大头。
  - **不存原文，只存链接和摘要**：网页会失效；AI 层无法重新生成；AI 提出的关联无法回到原文核对。
  - **把 AI 算出的关联写进笔记或存成链接**：会造成 ADR 0018 所说的幽灵链接，污染人的图谱。
  - **一开始就做分块 RAG 或引入向量数据库**：个人规模下卡片级向量加全文检索足够，复杂度不值得。
  - **把 PDF 与网页快照存进 vault**：会让 git 和外部同步持续变重。
