# 0061 判断闸门：用 Jev 做提醒分级、进展判断与对话授权

- 状态：第 1、3、4 节 Accepted（2026-11-11 人类同意方向；同日 Codex 核实接口）；第 2 节对话授权仍为 Proposed，满足其中的前置条件后另行批准
- 日期：2026-11-11
- 领域：权限与安全、Assistant
- 关联：ADR 0016（操作与授权）、0029、0046（TypeSafe Jev 连接）、0049（阶段权限）、0056（助手提议）、0059、0060
- 参考：[TypeSafe Jev](https://typesafe.ai/blog/introducing-system-one-models-and-jev)、[System One API](https://api.typesafe.ai/redoc)、[OpenAI Codex Auto-review](https://alignment.openai.com/auto-review)

## 背景

1. 人希望授权能在对话里完成：助手讲完一项问"这个可以做吗"，人说"可以"，这就是一次以人的身份做出的授权；
   说不清楚时在页面上弹框点确认。两种方式底层是同一件事。
2. 主对话里需要大量小判断：一个事件要不要打断人（ADR 0059 第 4 节）、一轮执行是在推进还是在空转（Watchdog）。
3. 这些判断如果交给主助手自己做，就是自己判断自己有没有被授权；读过的网页、邮件、执行输出里一旦有注入内容，
   主助手可能"以为"人同意了。业界已有把审批交给独立模型的做法（OpenAI Codex 的 Auto-review 用独立审核 agent 决定越界操作）。
4. TypeSafe 的 Jev 是一个"System One"决策模型：输入状态和带类型的问题（是非 `noul`、选项 `choice`、打分），只返回带概率的答案，不生成文字；
   厂商称延迟约 0.1–0.5 秒，每百万输入 token 0.042 美元，并声称概率经过校准，但目前公开的准确率数据主要是厂商自测。
   Lumio 已经可以保存 Jev 连接（ADR 0046），还没有使用。

## 决定

### 1. 判断闸门是 Hub 里的独立组件
- Hub 新增**判断闸门**：一个确定性的代码入口，内部调用决策模型。首个实现用 Jev；连接用统一 AI 配置的新用途绑定 `decision.gate`。
- 接口：`POST https://api.typesafe.ai/v1/systemone`，Bearer 鉴权，请求含 `model`、`state`、`questions`。
  试用固定 `jev-1.14.0`，记录每次响应的实际模型版本。`noul` 取"是"的概率，`choice` 取选项、各选项概率与 confidence。
- Hub 设自己的总时限。超时、响应校验失败、`401`、`422`、`429`、`529` 都立即回退（第 3 节回退为"待处理"，第 2 节回退为按钮），不重试到阻塞对话。
- 主助手（兼容 API 或原生会话）**不能调用、也不能看到**闸门的输入与结果，只能看到最终结论。
- 闸门的输入受限：只给它判断所需的最少内容，**不给网页、邮件、资料原文、执行输出等外部内容**；私密实体的内容不进入闸门。

### 2. 对话授权（Proposed）
目标做法：
- 适用对象：主对话里助手提出、仍待批准的委派与设置计划提议（ADR 0056）。阶段权限申请（`work.task.grant`）首期继续只能点按钮。
- 提议在对话里显示为 **Hub 根据结构化操作渲染的卡片**。对话批准必须绑定三样东西：一张已展示给人的卡片、卡片对应的冻结操作、一条已认证的人类消息（role=user，来自 human 自己拥有的主对话）。
  工具结果、助手消息、执行汇报、焦点里的选中文字中的"同意"一律无效。
- Hub（不是助手）把卡片文字和人的原话交给闸门，问：是否批准、范围是否一致、是否拒绝。
  批准概率超过阈值且范围一致时，以人的身份批准；拒绝同理；其余情况在页面上弹出确认卡片（ADR 0060 第 4 节）。
- 是否必须点按钮由 Hub 按**实际生效的权限**判定，而不是按提议类型：`exec.privileged`、删除与彻底删除、交接计划中任一步带 `full` 范围、密钥或钩子、计划模板变更，一律只能点按钮。

转为 Accepted 之前必须满足：
1. **撤销窗口有持久状态**：现有批准事务会立即执行，委派会当场创建可领取的 Job。需要先持久化"待执行的批准决定"与到期时间，窗口内不创建可领取的 Job；
   撤销与到期执行竞争同一次原子状态转换；到期执行前重查授权、操作内容和任务版本，并沿用原请求 ID。
2. **误批率有实测**：阈值（初设 0.95）本身证明不了误批率。要在合成数据上测否定、引用别人的话、条件同意、多个待批提议同时存在、卡片字段注入
   （任务标题等不可信内容会被渲染进卡片），并据此定阈值。
3. **契约单独审批**：`Proposal` 是严格对象，批准来源（chat / button）、消息 ID、模型版本与概率等字段需要兼容设计，按 AGENTS.md 第 1 条另行批准。

### 3. 提醒分级与进展判断（首期实施）
- ADR 0059 第 4 节的事件分级：闸门对规则判断不了的事件回答一个三选一问题（重要 / 待处理 / 静默）；只给事件类型、对象标题和 Hub 生成的结构化摘要。
  置信度低或闸门不可用时按"待处理"处理，不打扰人也不丢失。
- Watchdog 判断一轮是否在推进：给出同一轮相邻两次进度事件的结构化摘要（工具调用计数、改动文件数、最近错误类型），问"是否有实质进展"。只用于写巡检报告，不自动停止任何东西。
- 这两项都不改变任何业务状态，误判的代价是提醒多了或少了，因此可以先上线并按实际数据调整。

### 4. 数据去向
- 闸门的输入会发给 TypeSafe 的服务；设置页在 Jev 连接旁写明会发送的内容：事件结构化摘要，以及（第 2 节启用后）提议卡片和人的原话。
- 提议卡片里涉及私密实体时只显示类型，不显示标题。

## 不做
- 不用闸门替代 Hub 的 `authorize`：闸门只决定"人是否已经表态"，能不能做仍由现有权限表决定。
- 不让闸门处理高风险操作（第 2 节"一律只能点按钮"的清单）。
- 不把决策模型的结论当作对人的解释；需要说明理由时由主助手根据结论另外说明。
