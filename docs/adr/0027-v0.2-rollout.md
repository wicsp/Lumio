# 0027 v0.2 上线：Web 随安装运行、助手模型配置、旧任务笔记直接退役

- 状态：Accepted（2026-11-02 人类在对话中批准）
- 日期：2026-11-02
- 领域：Hub 与运行 | 安全 | 工程基础
- 影响：DESIGN 第 4.5、4.7、4.8 节；`install.sh`、`release.yml`、`apps/web`、`apps/hub`（setup、assistant、migrate）、`apps/cli`（upgrade、doctor、selftest）。不改 `packages/schema`。
- 实施说明：[R1-0](../tasks/R1-0-v0.2-release.md)

## 背景

四模块重构（ADR 0025）与 Web 工作台（ADR 0026）已合入 main，但作者实际在用的仍是 v0.1.6：

1. Web 只能在仓库里 `bun start`，发布包没有它，安装器和升级也不管它。
2. 助手模型只能靠手动修改 Hub 后台服务的环境变量配置，没有命令；文档要求「凭据仅运行时环境注入」，却没给出注入的办法。
3. 从任务笔记切换到数据库要按 `docs/migration-v2.md` 手动执行十余步。作者的旧任务、项目、例行笔记都是 P2 验收时建的测试数据，不需要保留为数据库对象。

作者的要求是尽快真正用起来，并且安装、升级不需要粘贴一串命令。

## 决定

### 1. Web 是安装的一部分
- 发布包增加第四个程序 `lumio-web`：`bun build --compile` 编译，浏览器 JS/CSS **在构建时嵌入**，运行时不再调用 `Bun.build`，也不读源码目录。
  仓库内 `bun start` 保持原样（开发时仍即时构建）。
- `lumio-hub setup` 在 Hub 所在机器上同时安装 Web 后台服务（macOS：launchd `io.lumio.web`；Linux：systemd 用户服务 `lumio-web.service`），
  监听 `127.0.0.1:4317`，上游为本机 Hub 的本地地址。服务器模式下 Web 同样只听本机，对外访问由部署者的反向代理负责（ADR 0022），
  此时 `LUMIO_WEB_ORIGINS` 取 `LUMIO_PUBLIC_URL` 对应的 Web 地址由部署者设置，setup 不猜。
- `lumio upgrade` 同时升级并重启 Web；`lumio doctor` 增加一项：Web 服务在运行、版本与 Hub 一致、能经代理访问 Hub 的 `/health`。
- 执行器机器不装 Web。`install.sh runtime` 不变。
- `setup` 结束时打印 Web 地址，并提示用 `lumio login-code --name web` 取一次性配对码。

### 2. 助手模型用命令配置，密钥放在 Hub 服务的环境文件里
- 新命令 `lumio-hub assistant setup`：交互式询问 API 地址、模型名和密钥。密钥用不回显的输入读取；非交互时只从标准输入读取（`--api-key-stdin`），
  **不接受命令行参数传入密钥**。地址规则与现有适配器一致（http/https，不含凭据、查询、片段）。
- 写入 Hub 后台服务的私有环境文件（与 Hub 现有令牌同一个文件，权限 600，原子替换），键名沿用
  `LUMIO_ASSISTANT_BASE_URL`、`LUMIO_ASSISTANT_MODEL`、`LUMIO_ASSISTANT_API_KEY`；然后重启 Hub 服务。
  这就是 DESIGN 所说的「运行时环境注入」的具体做法；密钥仍不进入仓库、`~/.config/lumio/config.json`、日志或命令输出。
- 写入前先用这组配置发一次最小请求验证（不保存对话、不计入业务数据）；失败时说明是地址、鉴权还是模型名的问题，不写入。可用 `--skip-check` 跳过。
- `lumio-hub assistant status` 只显示地址、模型和「密钥：已设置/未设置」；`lumio-hub assistant clear` 删除这三项并重启。
- `lumio doctor` 增加一项：助手已配置/未配置（未配置是提醒，不是失败）。
- 不预设供应商或模型（ADR 0025 第 7 节不变）。

### 3. 旧任务笔记可以直接退役，不导入
- 新命令 `lumio-hub migrate retire --vault <知识目录>`：**不导入**任何旧 Task/Project/Routine，只写入一条迁移回执，
  使该工作区的旧 Task/Routine 文件控制和 v1 任务派活/追问全部关闭（与首次 `migrate apply` 成功后的效果相同）。
- 执行前要求 Hub 已停止并独占状态目录（与 apply 相同），自动先做一次完整业务备份（`backup business`）并验证；
  回执里记录备份位置、退役时间和当时识别到的旧笔记数量与路径摘要。
- 旧笔记文件一律不改、不移动，继续作为普通知识文件可搜索、可阅读；之后新增或修改旧格式笔记也不会触发执行。
- 要求所有执行器上没有旧笔记派出、仍未交回的 Job；有则拒绝并列出。不要求逐条暂停或交回已结束的旧笔记。
- `migrate plan/apply` 保留，供需要导入的用户使用；同一工作区 retire 与 apply 只能二选一（已有回执时都拒绝）。

### 4. 一条命令完成切换
- `lumio upgrade` 发现 Hub 处于「v2 程序 + 旧笔记模式」时，在升级完成后提示两种选择（直接退役 / 按手册导入），
  并给出**一条**可直接运行的命令：`lumio-hub switch --retire-legacy`。它依次完成：停止 Hub 与本机执行器服务 → 本机执行器 `prepare-migration`
  → `migrate retire` → 启动服务 → `doctor`。任何一步失败即停止并说明已完成的步骤与恢复办法，不继续。
- 其他机器上的执行器只需各自 `lumio-runtime upgrade`（Job 协议仍为 2）；`switch` 列出仍在旧版本的已登记执行器作为提醒。
- `lumio selftest` 改用数据库任务（Work）验证派活与写回，`--notes` 改为创建数据库任务并在完成后标记 done；
  旧笔记模式下的自检路径删除。

## 后果

- 好处：新安装和升级后，浏览器直接打开 Web；助手一条命令接上；作者的切换只需 `lumio upgrade` 加一条 `switch`。
- 代价：发布包变大（多一个程序）；Hub 服务环境文件里多了一项第三方密钥，保护强度与 Hub 现有令牌相同，弱于系统钥匙串。
  以后需要钥匙串或外部密钥管理时另写 ADR。
- retire 之后旧笔记永远不再执行；需要找回旧任务时只能从退役前的业务备份或旧笔记原文手动重建。
