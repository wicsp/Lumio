# 0055 语音：浏览器采集、Hub 中转、语音服务并入 AI 配置底座

- 状态：Accepted
- 日期：2026-11-11
- 领域：AI 协作与权限 | 安全 | Hub 与运行
- 关联：ADR 0027（Hub 提供 Web）、0041（Connection / Profile / 用途绑定）、0042（原生会话）、0051（AI 笔记与来源）；任务 S1-0、G1-0

## 背景

人希望躺着用手柄操作 Lumio（G1-0），但很多安排要靠说话完成。此前（2026-11-08）的做法是语音交给人自己的输入法、与 Lumio 解耦。
为了用手柄唤起输入法，讨论过两条路，都不理想：

- **Karabiner 把某个手柄键映射成输入法快捷键**：Karabiner 要改手柄事件就得独占设备，浏览器的 Gamepad API 很可能因此读不到其余按键；只在装了 Karabiner 的 Mac 上有效。
- **网页请 Runtime 在系统层模拟按键**：只有本机有 Runtime 时可用，iPad、手机上没有；还需要辅助功能权限，并给 Runtime 增加"注入系统按键"这种高风险能力。

人在 2026-11-11 决定把语音做进 Lumio，并要求一并讨论延迟、带宽、流式、API 与本地部署、语音合成。
本 ADR 只为架构级部分做决定：新的流式协议、语音服务如何配置、音频与第三方的隐私边界、语音合成的总体方式。
界面细节与手柄键位写在任务说明里。

## 决定

### 1. 链路：浏览器采集，Hub 中转，Runtime 不参与

```
浏览器麦克风 ──WebSocket（PCM16）──▶ Hub ──▶ 语音识别服务（ASR）
     ▲                                 │
     └──── 中间结果 / 最终文本 ◀────────┘
```

- 录音只在浏览器里做（`getUserMedia` + AudioWorklet），因此桌面、iPad、手机上的 PWA 都能用，不依赖本机 Runtime。
- 浏览器只连 Hub，不直连第三方语音服务：服务的 API 密钥只在 Hub（与 ADR 0041 一致），浏览器拿不到。
- Runtime 不提供"模拟系统按键"能力。人自己的输入法照常可用，与 Lumio 内置语音并存。
- 识别结果只填入当前输入框，由人确认后再发送或保存；语音本身不触发任何操作（见第 5 节）。

### 2. 传输协议：`/v2/speech/transcribe`（WebSocket）

- **音频格式**：16 kHz、单声道、16 位小端 PCM，每帧 20–100 ms（约 0.6–3.2 KB）。码率 256 kbps，经 Tailscale 或公网都不构成瓶颈；
  首版不做浏览器端压缩，Hub 拿到即可转发，不必解码。以后需要省流量时再协商 Opus，作为协议新增字段，不改变首版语义。
- **控制消息**为 JSON 文本帧，音频为二进制帧。契约在 `packages/schema` 定义（新增 `speech.ts`），严格对象：
  - 浏览器 → Hub：`start`（认证、`request_id`、可选 Profile、语言提示、本次热词选择）→ 若干音频帧 → `end` 或 `cancel`。
  - Hub → 浏览器：`ready`、`partial`（序号 + 当前整句的临时文本，后一个覆盖前一个）、`final`（定稿文本）、`error`（带 `code` 的 `ApiError`）。
- **认证**：浏览器的 WebSocket 不能设置 `Authorization` 头，令牌放在第一条 `start` 消息里；Hub 在收到有效 `start` 前不接受音频，
  握手后 5 秒内没有有效 `start` 即断开。握手请求仍按 Web 现行规则校验 Origin/Host（ADR 0027）。
- **上限**：一句最长 120 秒，超出时 Hub 定稿并结束；单帧上限 8 KB；每个身份同时最多 2 路；空闲 10 秒无音频即结束。上限是常量，写进契约说明。
- **延迟预算**（流式服务）：分帧 ≤ 100 ms + 网络 + 服务出第一个临时结果 200–500 ms；松手到定稿目标 ≤ 1 秒。Hub 在远程时多一跳网络，不改变协议。
- 协议与 Job 协议、原生会话协议独立，有自己的版本号；不复用 `/v2/assistant/chat` 的 NDJSON。

### 3. 语音服务并入 AI 配置底座（扩展 ADR 0041）

- 语音识别和语音合成作为**新的用途**：`speech.asr`、`speech.tts`。仍是 Connection（来源与凭据）→ Profile（模型与参数）→ 用途绑定三层，
  不另起一套配置；设置页「AI 模型」里统一管理。
- **云端 API 是默认**：开源后的用户只填一个密钥就能用，符合"安装简单"的要求。首个服务商在 S1-1 中实测（中英混说、技术词、延迟）后选定，
  新服务商作为 `AIConnectionKind` 的新值加入。
- **本地模型是可选服务商**：放在某台 Runtime 上（Connection 的 `host` 为 Runtime 名，与原生 Codex 连接同一套规则），音频经 Hub 转给该 Runtime。
  首版不做；做时由 Runtime 声明能力，Hub 不负责安装模型。共享的实验室 GPU 不作为默认。
- **热词**：每个人维护一张词表（项目名、执行器名、常用术语、citekey 等），用来提高准确率。
  服务商要求先建词表的（首个服务商 Fun-ASR 即是），由 Hub 把词表同步到服务商保存的词表，请求只带词表 ID；其他服务商随请求发送。
  设置页注明"词表会保存在服务商"。
  单个热词按 Fun-ASR 的规则限制：含中文等非 ASCII 字符时最多 15 个字符，纯 ASCII 时最多 7 个以空格分隔的单词，总长不超过 40；每份词表最多 200 条。
  词表只来自人显式维护的条目和非私密的项目名；**不得**自动从知识正文或 `life/` 下的私密实体取词，因为热词会发给第三方并由其保存。
- **首个服务商**（S1-1，2026-11-11 人类选定）：阿里云百炼 Fun-ASR-Realtime，默认北京区域；连接类型 `dashscope`，地址只接受官方区域地址。
- 语音与模型推理是不同的服务：一个 Profile 只能绑定到与其类型相符的用途，不能把聊天模型绑成 ASR。

### 4. 隐私：不存音频，第三方明示

- **不保存原始音频**：音频只在 Hub 内存中按帧转发，一句结束即丢弃；不写盘、不进日志、不进备份。中间结果同样不保存。
- Hub 日志只记录会话元数据：身份、Profile、时长、字节数、结果状态，不记录文本内容。
- 最终文本在人发送或保存之后，才按所在位置（对话、任务说明、笔记）的既有规则保存；Lumio 不另存一份"语音转写记录"。
- 音频会发给所选的第三方服务商。设置页在语音 Profile 旁写明"音频将发送给 <服务商>"；没有配置语音 Profile 时，麦克风入口不出现。
- **只有 human 可以使用语音接口**。agent、runtime 身份请求 `/v2/speech/*` 一律拒绝，语音不进入能力目录。

### 5. 语音只产生文本，不直接执行

- 识别结果进入输入框，与键盘输入等价；需要批准的操作照常经提议与人的确认，语音不能替代确认。
- 文本的来源标记（人 / AI / 工具）不变：经语音输入、人确认后发送的仍是人的消息。是否另外标注"经语音输入"留待以后决定，不在本 ADR 中改契约。
- 识别不确定时不做猜测性的纠错改写；LLM 纠错与"找出所提到的知识条目"属于后续切片（S1-5），结果作为附加建议展示，由人选择是否采用，符合 ADR 0018 / 0051 的"AI 推荐、人决定"。

### 6. 安全上下文：麦克风需要 HTTPS 或 localhost

浏览器只在安全上下文（HTTPS 或 `localhost`/`127.0.0.1`）中允许麦克风。Lumio 不负责 HTTPS（ADR 0007、0022），因此：

- Web 检测到非安全上下文时，不显示录音入口，并说明原因和常见做法（例如 `tailscale serve` 或反向代理），不尝试绕过。
- 文档写明"语音功能需要 HTTPS 访问"。

### 7. 语音合成：串联方式，不用端到端实时语音模型

- 采用 **ASR → LLM → TTS 串联**：Assistant 的回复按句切分，逐句交给 TTS，浏览器边收边播；人按下说话键时立即停止播放（打断）。
- 朗读的是 Assistant 另行给出的**口语摘要**，不朗读 markdown、代码、diff 或完整 argv。
- 合成的音频同样不保存。
- **否决端到端实时语音模型**（语音进、语音出的 realtime 模型）：它在模型内部完成理解与回复，绕过 Lumio 的文本记录、能力目录、权限表与来源追溯；
  Assistant 的工具调用、审批与原生 Codex 会话都建立在文本轮次上。以后若要采用，需另写 ADR 说明如何保持这些边界。
- TTS 的协议与界面在 S1-6 之前另行细化；本节只确定方式与边界。

## 后果

**好处**

- 所有设备上都能语音输入，包括没有 Runtime 的 iPad 和手机；手柄的"按住说话"成为纯网页功能（G1-0），不需要 Karabiner，也不需要 Runtime 注入按键。
- 语音服务沿用 Connection / Profile / 用途绑定，密钥位置、设置界面、换服务商的方式都与现有 AI 配置一致。
- 音频不落盘，第三方服务明示，只有 human 能用；与现行权限和隐私规则一致。

**代价**

- Hub 第一次需要支持 WebSocket，并维持长连接与上限；需要在 S1-1 中验证 Bun 的实现与现有 CSP、Origin 校验能否配合。
- 语音功能要求 HTTPS，纯 HTTP 访问的部署看不到这个功能。
- 首版只接一家云端服务；中英混说的准确率取决于服务商与热词，可能需要后续纠错切片补足。
- 内置语音与人自己的输入法并存，入口多了一个，需要在界面上说明二者的区别。

## 否决的方案

| 方案 | 否决原因 |
|---|---|
| Karabiner 把手柄键映射成输入法快捷键 | 独占手柄设备，可能导致浏览器读不到其余按键；只适用于装了 Karabiner 的 Mac |
| Runtime 模拟系统按键唤起输入法 | 依赖本机 Runtime，移动端不可用；给 Runtime 增加注入系统按键的高风险能力；需要辅助功能权限 |
| 浏览器直连语音服务商 | 第三方密钥会暴露给浏览器；无法统一审计与限流 |
| 浏览器内置的 Web Speech API | 各浏览器实现与隐私去向不一致（Safari / Chrome 各自把音频发给自己的服务），不能选服务商、不能加热词 |
| 端到端实时语音模型 | 见第 7 节 |
