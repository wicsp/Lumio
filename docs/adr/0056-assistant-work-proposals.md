# 0056 内置助手可提议委派任务与设置交接计划

- 状态：Accepted（2026-11-11，人类批准）
- 日期：2026-11-11
- 领域：Assistant、Work 能力契约
- 关联：ADR 0029（能力目录）、0032（任务与交接计划）、0042（原生会话）

## 背景

Hub 已允许 agent 经 Work 命令提交任务委派和交接计划提议，CLI 已有对应命令。兼容 API 助手和原生 Codex 助手从共享能力目录加载工具，两项操作目前都未注册。能力执行层也需要把需要批准的 Work 写入交给现有提议流程。

## 提议

1. 将 `work.task.dispatch` 和 `work.task.plan.set` 注册为写入能力，沿用既有 `WorkTaskDispatch`、`WorkTaskPlanSet` 参数及 `WorkCommandResult`。能力名称允许一级子动作，以保留设置计划的现有命令名。用已有的任务详情和委派目标查询获取任务版本、现有计划和可用目标。
2. 助手按自身 agent 身份调用 `WorkCommands`。需要批准时返回 `kind: proposal` 和提议 ID，由 Hub 保存提议与审计。人批准后，Hub 按原作者、原请求 ID 和提议中的任务版本执行。批准设置计划只保存计划。工具说明明确提议何时生效。
3. 兼容 API 助手和新建原生会话从同一目录发现两项工具。已有原生会话继续使用创建时的工具集合，需要新建会话才能使用新增工具。CLI 沿用 `task continue` 和 `task plan set`，并通过现有生成流程将命令与能力关联。
4. 保留现有 Work 授权、提议决定入口及数据格式。复用委派目标、版本校验和请求去重规则。

## 验证

- 用契约测试校验两项工具的参数、结果与目录注册，验证 CLI 绑定和生成文档。
- 在合成数据上验证兼容 API 工具和原生 MCP 的工具发现与调用。提议创建后任务和执行轮次保持原状，只有人能批准。批准委派后生成一轮执行，批准计划后保存计划且轮次数为零。覆盖任务版本过期与重复请求。
