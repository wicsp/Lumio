# 主线开发与本机部署

从最新的 `origin/main` 建立功能分支。每个 PR 经独立 review、完整 CI 和人类验收后合入 `main`；由谁 review、何时试用与合并由 Lumio 交接计划或人类安排（ADR 0049）。本机只维护一个日常实例，监听 `127.0.0.1:7420`，默认从 `main` 的已提交版本构建，有 PR 在试用时运行试用组合（见下文）。隔离测试使用临时目录、临时端口和合成数据。

更新日常实例前，确认 Hub 和 Runtime 的活跃工作已经结束。用 `lumio hub backup business <新目录>` 创建业务快照，并用 `lumio hub backup verify <目录>` 校验。备份当前程序、服务定义和 Runtime 状态供回退。涉及迁移时先用合成数据验证，并确认备份可恢复。业务备份、vault 与安装配置的边界见 [Hub 部署与备份](design/hub.md#存放)。

从指定提交的独立源码目录用仓库固定的 Bun 构建。安装新程序后重启 Hub。仅 Web 更新可保留 Runtime 进程；Runtime 有改动时，等在途工作结束后再重启。核对 `/health` 的版本、页面资源和 Runtime 在线状态。

对外发布时，从 `main` 上已验收的提交推送正式 `v*` 标签。Release workflow 校验提交属于主线，重跑全量检查并创建 GitHub Release。带预发布后缀的版本标为预发布，不成为 Latest。

## 在日常实例上试用 PR

试用直接部署在日常实例 7420 上，可以同时试用多个 PR。正在试用的 PR 以 GitHub label `trial` 为准，不靠记忆或其他记录。
日常实例运行的是**试用组合**：最新的 `origin/main` 依次合入所有带 `trial` 标签的 open PR。每次部署都按下面的步骤从头重新生成，不在上一次的组合上叠加。

被交代部署某个 PR 试用时：

1. 把该 PR 分支更新到最新的 `origin/main` 之上并推送，CI 以更新后的提交为准；然后给它加上 `trial` 标签（`gh pr edit <编号> --add-label trial`）。
   已在试用的其他 PR 保持原样，不需要更新。
2. 用 `gh pr list --label trial --state open` 列出试用中的 PR，在独立源码目录里基于最新的 `origin/main` 建一个本地临时分支，按 PR 编号从小到大逐个 `git merge --no-edit`。
   - **只做合并，不阅读、不审查、不修改其他 PR 的代码。**
   - 出现冲突时立即 `git merge --abort`，不要尝试解决；跳过这个 PR 继续合入其余的，并在汇报里写明它和哪个 PR 冲突。冲突怎么处理交回人决定。
   - 临时分支只用于本机构建，不推送，不合入 `main`。
3. 按上文创建并校验业务备份，在汇报里写明备份目录。组合里有 PR 含数据迁移、且这次是它第一次进入组合时，先停下交回人确认再部署。
4. 从组合的提交构建并按上文更新日常实例，核对 `/health` 的版本、页面资源和 Runtime 在线状态。
   在汇报里列出这次组合包含哪些 PR 和各自的提交号，以及被跳过的 PR。
   改动涉及 Runtime 时，部署由当前轮次触发会重启执行它的 Runtime：用脱离当前进程的方式重启，并在汇报里说明需要人确认 Runtime 已重新上线。

PR 试用不通过（打回或搁置）时，去掉它的 `trial` 标签，按上面第 2–4 步重新部署；它含迁移时从它进入组合前的备份恢复，试用期间写入的数据会丢失。
PR 合并后，`trial` 标签随 PR 关闭自然失效，按第 2–4 步重新部署，其余试用中的 PR 继续保留；没有试用中的 PR 时，部署的就是 `main`。
