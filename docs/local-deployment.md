# 主线开发与本机部署

从最新的 `origin/main` 建立功能分支。每个 PR 经独立 review、完整 CI 和人类验收后合入 `main`；由谁 review、何时试用与合并由 Lumio 交接计划或人类安排（ADR 0049）。本机只维护一个日常实例，监听 `127.0.0.1:7420`，默认从 `main` 的已提交版本构建。隔离测试使用临时目录、临时端口和合成数据。

更新日常实例前，确认 Hub 和 Runtime 的活跃工作已经结束。用 `lumio hub backup business <新目录>` 创建业务快照，并用 `lumio hub backup verify <目录>` 校验。备份当前程序、服务定义和 Runtime 状态供回退。涉及迁移时先用合成数据验证，并确认备份可恢复。业务备份、vault 与安装配置的边界见 [Hub 部署与备份](design/hub.md#存放)。

从指定提交的独立源码目录用仓库固定的 Bun 构建。安装新程序后重启 Hub。仅 Web 更新可保留 Runtime 进程；Runtime 有改动时，等在途工作结束后再重启。核对 `/health` 的版本、页面资源和 Runtime 在线状态。

对外发布时，从 `main` 上已验收的提交推送正式 `v*` 标签。Release workflow 校验提交属于主线，重跑全量检查并创建 GitHub Release。带预发布后缀的版本标为预发布，不成为 Latest。

## 在日常实例上试用 PR

试用直接部署在日常实例 7420 上，同一时间只试用一个 PR。被交代部署某个 PR 试用时：

1. 确认没有其他 PR 正在试用（7420 正在运行的版本来自 `main`），否则停下说明。
2. 把 PR 分支更新到最新的 `origin/main` 之上并推送，试用与 CI 以更新后的提交为准；在汇报里写明这个提交号。
3. 按上文创建并校验业务备份，在汇报里写明备份目录。PR 含数据迁移时，先停下交回人确认再部署。
4. 从该提交的独立源码目录构建并按上文更新日常实例，核对 `/health` 的版本、页面资源和 Runtime 在线状态。
   改动涉及 Runtime 时，部署由当前轮次触发会重启执行它的 Runtime：用脱离当前进程的方式重启，并在汇报里说明需要人确认 Runtime 已重新上线。

试用不通过（打回或搁置）时，从 `main` 重新部署；含迁移时从试用前的备份恢复，试用期间写入的数据会丢失。
合并后从 `main` 重新部署，版本号随之更新。
